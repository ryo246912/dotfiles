# PRのUI/UXレビュー

1. 指定PRまたはローカル差分のベースと変更後を取得する。PR説明、関連仕様、変更ファイル、既存画面から、対象ユーザー、主タスク、必須条件を確認する。UIへの直接変更に加えて、データ・権限・状態の変更による操作への影響も追う。UIへの影響が確認できなければ、その根拠を簡潔に返す。
2. プレビューが使える場合は変更前後で主な操作を試す。必要なエラー・空状態・再試行を確認し、操作が見つかるか、フィードバック、誤操作と復旧、キーボード・フォーカス・モバイルを確認する。観察した事実、差分からの推定、未確認事項を区別する。プレビューが使えない場合は差分と既存コンポーネントからレビューを継続する。
3. 問題ごとに、対象ユーザー、発生条件、具体的な不利益、確認方法、改善案を示す。差分に起因する指摘はファイルと行を付ける。既存課題が比較に影響する場合は既存であることを明示する。
4. 「明確な欠陥の修正」に加え、同じ目的をより少ない手順・状態・誤操作で達成する設計があるか検討する。改善が見込めるときは現PR案と、有力な代替案を通常1〜2個比較する。見た目だけで判断せず、挙動、ユーザー便益、制約、既存UIとの一貫性、追加の実装・テスト負担を根拠に判断する。画面構成や操作フローが判断を左右する場合は画像付きで比べる。代替の便益を裏付けられなければ、現PR案を支持できる理由を述べる。
5. 実測できた問題と設計提案を区別し、主タスクを阻む問題、今回修正する価値の高い改善、後続候補の順に示す。代替案の実装難易度は現在のPRからの追加分を低・中・高で示し、UI、API、データ、テストのどこが変わるかを書く。

## 依存スキルの呼び出し

- 画面・フローのレビューは Uxcel の `ux-design-review` を基本とする。必要に応じて Impeccable の `critique` または Vercel の `web-design-guidelines` を対象画面へ適用する。
- 操作仕様や代替案の検討には mblode の `product-design`。現PR案と具体的な代替案の比較には ysskrishna の `tradeoff-analysis`。
- 画像があると判断しやすい変更では、同じ rulesync 配布に含まれる `uiux-option-review` を呼び出し、現PR案と代替案を同一条件で可視化する。比較を作る前に、このPRで見えた制約と実際の差分を渡す。
- モバイルでの操作が重要で、プレビューが使える場合は利用可能な `pr-mobile-review` を呼び出す。
- 一覧から作者と完全名を確認して呼び出す。専用の呼び出し機能がない場合はインストール済みSKILL.mdを読み、必要な手順を実行する。不足している外部スキルは配布元の評価手順を参照し、取得できなければ上記のレビューを継続する。同梱スキルに直接アクセスできない場合は、同じデータ・画面幅・作り込みでモック画像を用意する。実行したスキル、公開手順の参照、未確認事項を明記する。
- 依存のインストール、PRへのコメント投稿、コード編集、コミットはレビューに含めない。外部レビューサービスへのコード転送はこのスキルの手順に含めない。

## 返すもの

重要な指摘を根拠とともに先に出し、現PR案と代替案の推奨、UXの差、追加実装難易度、必要な画像、確認範囲を続ける。ユーザーの選択が必要なら、何が決まると推奨が変わるかを示す。
