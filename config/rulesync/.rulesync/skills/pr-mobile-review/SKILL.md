# スマホ向けPRレビュー

## 対象を決める

- 指定されたPR、ブランチ、URLを使う。PR差分と説明から、変更画面、共通UIへの影響、主要な操作経路、必要なデータや認証状態を特定する。URLのみの場合は確認できる画面と操作を対象にする。
- PRのプレビュー、またはリポジトリの既存手順で対象をローカル起動する。確認したURL・コミットを記録する。プレビューとPRの一致を確認できない場合はその旨を記録する。
- 書き込みを伴う操作にはプレビューやローカルのテストデータを使う。

## 確認環境を選ぶ

1. Android実機にアクセスできる環境では、利用可能な `android-debug` ツールを優先する。ツールが提供されていなければ、端末にアクセスできるホストで `adb devices -l` を使って接続状態を確認し、承認済みで状態が `device` の実機をADBで操作する。複数台ある場合は指定端末を選び、指定がなければ対象端末を確認してから操作する。
2. 実機で対象プレビューを開き、端末上でタップ、スワイプ、入力、戻る操作を実行する。ローカルのWebアプリは既存の端末向け接続手順を使い、必要ならテスト用ポートに限ってADBのリバース転送を使う。自分で追加した転送は確認後に解除する。実機で確認できた画面と操作には実機の結果を採用し、端末の表示幅や密度はテストのために変更しない。
3. 実機を操作できない、または対象URLに到達できない場合は、その理由を記録してPCブラウザに切り替える。Claude in Chrome、Playwright MCP、または利用可能な同等のブラウザ操作ツールを使う。モバイル用ビューポートやタッチ入力を設定できるツールを優先する。幅だけ変更できる場合は表示を確認し、タッチ操作の確認範囲を明記する。
4. 実機で主要操作を確認できた場合も、その端末で確認できない幅の表示チェックはPCブラウザで補う。

## 幅を変えて表示を確認する

- 指定がなければ縦向きで 320×568、360×800、390×844、430×932 CSS px を使う。差分に関係するモバイルのブレークポイントがあれば、その直前と直後（±1 CSS px）も確認する。指定された端末や幅を優先する。
- 設定値と実際のCSSビューポート幅を照合する。幅ごとに変更画面を初期状態から表示し、メニュー展開、モーダル、入力エラー、長い文言など、差分に関係する状態も確認する。
- 意図しないページ全体の横スクロール、要素の重なり、文字の欠け・はみ出し・不自然な改行、画像や表のはみ出し、主要ボタンの画面外への押し出しを確認する。横スクロール領域は、意図された範囲内で最後の項目まで到達できるか確認する。
- ページの横はみ出しは必要に応じて `document.documentElement.scrollWidth` と `clientWidth` を比較する。数値に差がなくても、要素内部の文字切れや重なりは目視する。

## タッチ操作を確認する

- 実機では主要操作を端末の通常設定で実行する。PCで操作を確認する場合はタッチエミュレーションを有効にし、狭い幅と代表的な幅（既定では320 pxと390 px）で主要操作を実行する。幅によってUIや問題が変わる場合は該当幅でも操作する。
- ボタンやリンクをタップし、押せる領域と隣接要素の間隔、片手での届きやすさ（実機で確認できる場合）、誤タップ、ホバー前提の機能、タップ後の反応を確認する。カルーセルやドラッグが変更対象なら、利用可能なタッチ入力で操作し、縦スクロールとの干渉も確認する。
- スクロールしながら固定ヘッダーや下部バーが内容やボタンを覆わないか確認する。モーダルやメニューの内部スクロール、閉じる操作、閉じた後に元の画面へ戻れることも確認する。
- フォームは入力、フォーカス移動、エラー表示、送信ボタンへの到達を確認する。ソフトウェアキーボードで要素が隠れるか、端末のセーフエリアやOSのジェスチャーと干渉するかなど、環境で再現できない項目は実機での確認事項として明記する。実機では端末モデル・Androidバージョン・ブラウザを記録し、PCではブラウザエンジンとエミュレーション方法を記録する。

## 結果を報告する

- 指摘はユーザーへの影響が大きい順に並べる。各項目に画面・状態、再現した幅とブラウザ、再現手順、実際の挙動と期待される挙動を含める。取得できればスクリーンショット、差分から原因を特定できればファイルと行番号を添える。
- 確認した画面・幅・操作と結果を簡潔にまとめ、Android実機とPCブラウザのどちらで確認したかを項目ごとに示す。操作はできても押しづらい、余分なスクロールが必要など、スマホでの使いづらさも再現手順とともに報告する。問題が見つからなかった場合も確認範囲を示す。認証や環境の制約、未実施の幅・操作、実機確認が必要な項目を記録する。
- レビュー結果は依頼元に返す。コード修正やPRへの投稿は依頼がある場合に行う。
