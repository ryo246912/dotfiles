# pr-reviewer-brief — レビュー前に読む PR の解説資料を HTML で作る

レビューに入る前に、**その PR が何を変え、なぜ変え、どう確かめるか**を、コードベースを知らない人にも分かる形で
1 枚の HTML にまとめる。この skill は**説明に徹する**。良し悪しの指摘はしない。GitHub への投稿・ラベル変更・push もしない。

トークンを抑えるため、作業を段階に分け、段階ごとに合うモデルの subagent に任せる。モデルが書くのは JSON（中身）だけで、
HTML・図の座標・差分の表はスクリプトが作る。各段階の手順は `references/` にあり、**その段階を担当する subagent だけが読む**。

## 引数

`/pr-reviewer-brief <対象>` または `/pr-reviewer-brief --watch`

| 書き方                   | 対象                                                            |
| ------------------------ | --------------------------------------------------------------- |
| PR の URL、`123`、`#123` | その PR。gh stack の stack に入っていれば、その stack 全体      |
| `stack 7`、`stack #7`    | gh stack の stack 番号（github.com の stack の UI に出る番号）  |
| `--watch`                | 新しく作られた PR を監視して資料を作る（`references/watch.md`） |

番号だけなら PR 番号とみなす（stack 番号のときは `stack` を付けてもらう）。リポジトリはカレントディレクトリのものとみなす。
ほかの指定（スクリーンショットを撮るか、撮る先の URL、使うモデルなど）は、ユーザーの自然文から読み取る。

## 進め方

| 段階 | 担当                                  | 読む手順                    | 作るもの（作業ディレクトリ）                   |
| ---- | ------------------------------------- | --------------------------- | ---------------------------------------------- |
| 0    | メイン                                | この SKILL.md               | `target.json`                                  |
| 1    | subagent（`haiku`）                   | `references/collect.md`     | 差分・hunk・変更グループの下書き・引き継ぎメモ |
| 2    | subagent（`sonnet`）                  | `references/write.md`       | `brief.json`・仕上げた `groups.json`・**HTML** |
| 3    | subagent（`haiku`）。頼まれたときだけ | `references/screenshots.md` | スクリーンショットを撮り、HTML を作り直す      |

### 段階 0: 対象を決める（メイン）

```bash
python3 <この skill のディレクトリ>/scripts/get_stack.py --pr <PR 番号>      # または --stack <stack 番号>
```

- 出力の `is_stack` が true なら名前は `stack-<stack_number>`、false なら `pr-<N>`
- **作業ディレクトリ** `./plan/.pr-reviewer-brief/<名前>/` を作り、出力をそのまま `target.json` に保存する
- **出力先**は `./plan/<名前>.html`
- `warnings` があれば、段階 2 への依頼に「未確認事項に書く」として添える

### 段階 1〜3: subagent に任せる（メイン）

Agent ツールで、段階ごとに subagent を **1 つずつ順に**起動する（フォアグラウンド）。依頼文は次の形にし、コードや差分は
メインで読まない。

> `<この skill のディレクトリ>/references/<手順ファイル>` を読み、その手順で進めてください。
> skill のディレクトリ: `<この skill のディレクトリ>` / 作業ディレクトリ: `<作業ディレクトリ>` / 出力先の HTML: `<出力先>`
> （監視モードなら）監視モードから呼ばれています。ユーザーに質問せず、決められないことは仮定を置いて `unknowns` に書いてください。
> 最後に、手順の「終わり方」のとおり 1 行だけ返してください。

- **モデルの選び方**: 段階 1 と 3 は `haiku`。段階 2 は既定で `sonnet`。段階 1 が返した `lines`（追加+削除）が 300 未満なら
  `haiku` でよい。ユーザーがモデルを指定したら（「全部 haiku で」など）それに従う
- 段階 1 が失敗したら、その内容を伝えて止める。段階 2 の検査エラーは段階 2 の中で直させる
- subagent を使えない環境（Codex など）では、メインが同じ順に手順ファイルを読んで進める

### 終わったら（メイン）

HTML のパスを伝え、`brief.json` の `tldr` と、`groups.json` のグループ一覧（番号・タイトル・risk）を短く出す。
Claude Code で Artifact として公開できる環境なら、ユーザーに確認したうえで公開してよい。

## 監視モードのルール

`--watch`（`references/watch.md`）から作るときは、次を守る。

- ユーザーに質問しない。決められないことは仮定を置いて進め、仮定を「未確認事項」に書く
- 出力先に同じ名前の HTML があり、`<meta name="pr-reviewer-brief-head">` が `target.json` の `top_head_sha` と同じなら、
  何もせず終える
- スクリーンショットは撮らない

## してはいけないこと

- GitHub へ投稿しない（コメント・レビュー・ラベル・状態の変更を含む）。他人のブランチへ commit / push しない
- コードを編集しない（調べるための読み取り・テスト実行は可）
- 根拠のない「今はこう動く」を書かない
- HTML や SVG を手で書かない（`brief.json` を直して `render_brief.py` で作り直す）
