## ヘルプ・引数

`-h` / `--help` があれば、他の引数より優先してこの節の使い方・全オプション・既定動作と終了条件を説明し、その場で終了する。PR の取得、監視、編集、スクリプト実行、commit・push・投稿は行わない。これらは skill の引数であり、内部 CLI のオプションは含めない。不明なオプションでは処理を開始せず、このヘルプを表示する。

使い方: `/pr-reviewer-brief <PR・stack> [-be / --behavior]`、`/pr-reviewer-brief <チケット>`、または `/pr-reviewer-brief --watch`

| 引数                | 意味                                                             |
| ------------------- | ---------------------------------------------------------------- |
| `-h`, `--help`      | ヘルプのみ表示して終了                                           |
| `-be`, `--behavior` | 起動済み環境での動作確認を追加。PR・stack の指定時のみ           |
| `--watch`           | 新しく作られた PR を継続監視して説明資料を作る。Claude Code 専用 |

既定では資料だけを作成する。`-be` / `--behavior` を指定すると起動済み環境での動作確認を試み、実結果を資料に取り込む。`--watch` はユーザーが停止するまで監視を繰り返す。1 回の監視プロセスは対象がなければ既定 110 分で終了し、監視モードは再開する。

# pr-reviewer-brief — レビュー前に読む PR の解説資料を HTML で作る

skills schema version: **1.3**（生成 HTML の生成日時の横にも表示）。
前提知識の ER 図は Mermaid の `erDiagram` で作り、今回関係する画面の表示データに関わるテーブルを必ず載せる
（DB と無関係な表示のみなら、その事実と根拠を記載）。左側の目次には前提知識の小見出しへのリンクも出す。
表示順は TL;DR → 変更の範囲 → 絵で見る → 前提知識（ER図を含む）→ 変更内容 → スキーマ・API・設定の差分 → 動作確認方法 → スタック構成 → 変更グループ → 重点的に見る箇所 → 未確認事項。内容のない章は省略する。

レビューに入る前に、**その PR が何を変え、なぜ変え、どう確かめるか**を、コードベースを知らない人にも分かる形で
1 枚の HTML にまとめる。説明に加え、pr-reviewer-behaviorで実施したデータ準備と動作確認を事実として報告する。

トークンを抑えるため、作業を段階に分け、段階ごとに合うモデルの subagent に任せる。briefレポートの中身はJSONで書き、
HTML・図の座標・差分の表はスクリプトが作る。この制約はbehaviorが補完する設定や知見Markdownには適用しない。各段階の手順は `references/` にあり、**その段階を担当する subagent だけが読む**。

## 引数

引数の組み合わせは「ヘルプ・引数」を参照する。

| 書き方                    | 対象                                                                              |
| ------------------------- | --------------------------------------------------------------------------------- |
| PR の URL、`123`、`#123`  | その PR。gh stack の stack に入っていれば、その stack 全体                        |
| `stack 7`、`stack #7`     | gh stack の stack 番号（github.com の stack の UI に出る番号）                    |
| `ABC-123`、チケットの URL | チケット（Linear・Notion・Jira・GitHub Issue など）。**チケットモード**になる     |
| `--watch`                 | 新しく作られた PR を監視して資料を作る。Claude Code 専用（`references/watch.md`） |

番号だけなら PR 番号とみなす（stack 番号のときは `stack` を付けてもらう）。`ABC-123` のように英字と `-` を含む ID、
Linear・Notion・Jira・GitHub Issue の URL、`ticket <ID>`（先頭の `ticket ` は除く）はチケットとみなす。リポジトリはカレントディレクトリのものとみなす。
チケットや `--watch` に `-be` / `--behavior` を組み合わせた場合は、処理を開始せず使い方を表示する。
PR・stack では段階 0〜2 を実施する。段階 3 は明示指定で動作確認するとき、または渡された結果を取り込むときに実施する。確認先 URL や使うモデルはユーザーの自然文から読み取る。

## 前提知識の調査範囲

前提知識（ER 図を含む）は表示する diff の範囲に限らず、PR モードでは PR の base、stack モードでは stack 全体の base（trunk）、チケットモードでは default branch を対象とする。
最上位 PR の diff だけで DB との関連を判断しない。stack 内の他 PR と、関連する既存 API・取得処理・モデルまで辿る。

## 進め方

| 段階 | 担当                                           | 読む手順                    | 作るもの（作業ディレクトリ）                                       |
| ---- | ---------------------------------------------- | --------------------------- | ------------------------------------------------------------------ |
| 0    | メイン                                         | この SKILL.md               | `target.json`                                                      |
| 1    | subagent（`haiku`）                            | `references/collect.md`     | 差分・hunk・変更グループの下書き・チケット・引き継ぎメモ           |
| 2    | subagent（`sonnet`）                           | `references/write.md`       | `brief.json`・仕上げた `groups.json`・**HTML**                     |
| 3    | subagent（`sonnet`）。execute / reuse 時に実施 | `references/screenshots.md` | behaviorによるデータ準備・実動作確認、画像・結果の統合、HTML再生成 |

### 段階 0: 対象を決める（メイン）

```bash
python3 <この skill のディレクトリ>/scripts/get_stack.py --pr <PR 番号>      # または --stack <stack 番号>
```

- 引数は数字だけにして渡す。PR の URL なら `/pull/` の後ろの番号を、`#123` なら `#` を除いた番号を使う

- 出力の `is_stack` が true なら名前は `stack-<stack_number>`、false なら `pr-<N>`
- **作業ディレクトリ** `./plan/.pr-reviewer-brief/<名前>/` を作り、出力をそのまま `target.json` に保存する
- **出力先**は `./plan/<名前>_<変更内容タイトル>.html`（例: `pr-123_土地一覧の検索条件を追加.html`）。
  `<変更内容タイトル>` は段階 2 で決める `brief.json` の `title` を使う。stack・チケットも同じ命名にする。
  ファイル名に使えない文字（`/`・`\`・`:`・`*`・`?`・`"`・`'`・`` ` ``・`$`・`<`・`>`・`|`・制御文字）は `-` に置き換え、
  前後の空白と末尾の `.` を除く。ファイル名全体（接頭辞・区切り・拡張子を含む）が UTF-8 で 255 バイト以内になるよう、タイトルの末尾を文字単位で切り詰める。空になった場合は `変更内容` とする。作業ディレクトリ名は変えない。
- メインは `behavior_mode`（`execute` / `reuse` / `skip`）と省略理由 `behavior_skip_reason` を `target.json` に追記する。単体では対象が PR・stack で `-be` / `--behavior` がある場合だけ execute とする。「説明だけ」「動作確認不要」、チケット、監視では skip とする。all-review が同じリポジトリ・対象範囲・SHA の観測を渡した場合は reuse とする。渡された未実施理由は skip の理由として残す。PR 本文からモードを決めない。
- `warnings` があれば、段階 2 への依頼に「未確認事項に書く」として添える

**チケットモード**（チケットの ID か URL を渡されたとき）は、`get_stack.py` を実行しない。

- 名前は `ticket-<ID>`（URL なら ID の部分。Notion なら page ID の末尾 8 文字。英数字と `-` 以外は `-` にする）
- 作業ディレクトリを作り、`target.json` に `{"mode": "ticket", "ticket": "<渡された ID か URL>", "behavior_mode": "skip", "behavior_skip_reason": "チケットモード"}` を書く
- 段階 1 は `references/collect.md` の代わりに `references/collect-ticket.md` を使う。段階 3（behaviorによる動作確認）は行わない
- 資料には TL;DR・スタック構成・前提知識・変更内容だけが出る

### 段階 1〜3: subagent に任せる（メイン）

Agent ツールで、段階ごとに subagent を **1 つずつ順に**起動する（フォアグラウンド）。依頼文は次の形にし、コードや差分は
メインで読まない（subagent に任せるときだけの決まり。下の Codex などの場合はメインが読む）。

> `<この skill のディレクトリ>/references/<手順ファイル>` を読み、その手順で進めてください。
> skill のディレクトリ: `<この skill のディレクトリ>` / 作業ディレクトリ: `<作業ディレクトリ>` / 出力先の HTML: `<出力先>`
> 段階3の実行モード: `<execute / reuse / skip>` / 省略理由: `<説明だけ・監視・チケット等。executeならなし>`。target.jsonの同じ項目も必ず渡す。reuse では受領済み観測を渡す。skip なら behavior を起動せず、実操作・データ変更を行わない。
> （段階 3 で、ユーザーが確認先の URL を指定していれば）確認先の URL: `<URL>`
> （監視モードなら）監視モードから呼ばれています。ユーザーに質問せず、決められないことは仮定を置いて `unknowns` に書いてください。
> 最後に、手順の「終わり方」のとおり 1 行だけ返してください。

段階 2 への出力先は `<名前>_<変更内容タイトル>.html` の形式で伝え、タイトル部分を確定させる。
段階 3 には、段階 2 が返した実際の HTML パスを渡す。段階3はexecuteの場合だけpr-reviewer-behaviorを実行し、別レポートへのリンクだけで終えず、準備・確認の構造化結果をbrief.jsonへ取り込んで同じHTMLを再生成する。BLOCKED時も段階3の終了前チェックを実施し、知見保存先と`lesson_capture`をメインが確認してから完了する。reuse は受領済み結果を取り込んで HTML を再生成する。skip の場合は計画を NOT RUN のまま残す。

- **モデルの選び方**: 段階 1 は `haiku`。段階 2 と 3 は既定で `sonnet`。段階 1 が返した `lines`（追加+削除）が 300 未満なら
  `haiku` でよい。ユーザーがモデルを指定したら（「全部 haiku で」など）それに従う
- 段階 1 が失敗したら、その内容を伝えて止める。段階 2 の検査エラーは段階 2 の中で直させる
- subagent を使えない環境（Codex など）では、メインが同じ順に手順ファイルを読み、必要なコードと差分も自分で読んで進める

### 終わったら（メイン）

HTML のパスを伝え、`brief.json` の `tldr` と、`groups.json` のグループ一覧（番号・タイトル・risk）を短く出す
（チケットモードでは `tldr` と関連する PR）。チケットが取れなかった（`ticket.json` の `fetched` が false、または MCP が
無かった）ときは、そのことと理由も 1 行で伝える。
動作確認を実施したか、準備済みデータ、判定と未確認事項も短く伝える。環境が未準備でもbriefの生成は完了し、behaviorで得た到達手順とBLOCKEDの理由を載せる。
Claude Code で Artifact として公開できる環境なら、ユーザーに確認したうえで公開してよい。

## 監視モードのルール

`--watch`（`references/watch.md`）から作るときは、次を守る。

- ユーザーに質問しない。決められないことは仮定を置いて進め、仮定を「未確認事項」に書く
- 出力先に `<名前>_*.html` に該当する HTML があり、`<meta name="pr-reviewer-brief-head">` が `target.json` の `top_head_sha` と同じなら、
  何もせず終える
- behaviorを起動せず、データ準備・ブラウザ操作・撮影はしない。手順はNOT RUNとして記載する

## してはいけないこと

- brief の作成手順では GitHub へ投稿しない。レビュー投稿は段階 4 で pr-reviewer-all-review の確認手順に従う。ラベル・状態変更や、他人のブランチへの commit / push は行わない
- コードを編集しない。段階3のテストデータ作成・設定補完・知見保存はpr-reviewer-behaviorの範囲で行う。環境起動・checkout・migration・feature flag変更・base比較はしない
- 根拠のない「今はこう動く」を書かない
- HTML や SVG を手で書かない（`brief.json` を直して `render_brief.py` で作り直す）
