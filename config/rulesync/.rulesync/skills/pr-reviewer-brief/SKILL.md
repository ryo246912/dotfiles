# pr-reviewer-brief — レビュー前に読む PR の解説資料を HTML で作る

レビューに入る前に、**その PR が何を変え、なぜ変え、どう確かめるか**を、コードベースを知らない人にも分かる形で
1 枚の HTML にまとめる。この skill は**説明に徹する**。良し悪しの指摘はしない（気づいた懸念は「重点的に見る箇所」に
事実として書くだけ）。GitHub への投稿・ラベル変更・push もしない。

全体の流れ:

1. 引数を読み、対象の PR（と stack）を確定する
2. PR の情報と差分を集める
3. 前提知識（今の機能・データモデル・用語）を調べる
4. 変更内容を整理し、絵にする
5. 差分を変更グループに分け、解説を付ける
6. 動作確認手順を書く（頼まれたらスクリーンショットも撮る）
7. HTML を書き出し、場所を伝える

## 引数

`/pr-reviewer-brief <対象>` または `/pr-reviewer-brief --watch`

`--watch` は、新しく作られた PR を監視して資料を作るモード（下の「監視モード」）。それ以外のとき、対象は次のどれか。

| 書き方                   | 対象                                                           |
| ------------------------ | -------------------------------------------------------------- |
| PR の URL、`123`、`#123` | その PR。gh stack の stack に入っていれば、その stack 全体     |
| `stack 7`、`stack #7`    | gh stack の stack 番号（github.com の stack の UI に出る番号） |

番号だけなら PR 番号とみなす（stack 番号と PR 番号はどちらも数字なので、stack 番号のときは `stack` を付けてもらう）。
リポジトリはカレントディレクトリのもの（`gh repo view --json nameWithOwner`）とみなす。

ほかの指定（スクリーンショットを撮るか、撮る先の URL など）は、ユーザーの自然文から読み取る。

## 1. 対象の PR と stack を確定する

gh stack（GitHub の Stacked PRs）の Stacks REST API で、stack とその PR を取る。

```bash
python3 <この skill のディレクトリ>/scripts/get_stack.py --stack <stack 番号> [--repo owner/name]
python3 <この skill のディレクトリ>/scripts/get_stack.py --pr <PR 番号> [--repo owner/name]
```

PR を下（trunk 側）から上への順で JSON に出す。`is_stack` が false（stack に入っていない、または repository で
Stacked PRs が有効でない）なら、その PR 単体として進める。

- merge 済みの PR は stack の一部として表に載せるが、差分は trunk に入っているので全体の差分には含めない
  （`diff_base` が、まだ merge されていない一番下の PR の base になっている）
- `warnings` があれば、その内容を「未確認事項」に書く

**stack の扱い方**: stack 全体を 1 つの PR とみなして読む。資料の主役は stack 全体の説明で、各 PR は
「スタック構成」の表で 1〜2 行にまとめるだけにする。ユーザーが PR 番号で指定したなら、その PR を表で強調する。

## 2. PR の情報と差分を集める

各 PR について:

```bash
gh pr view <N> --json number,title,url,state,author,body,baseRefName,headRefName,headRefOid,files,additions,deletions,labels,comments,reviews,closingIssuesReferences
gh pr checks <N>
```

差分は、単体の PR なら `gh pr diff <N>`。stack なら、一番下の PR の base から一番上の PR の head までを 1 つの差分として見る。
カレントディレクトリが対象リポジトリなら手元で取る（ファイルも読めるので、こちらを優先する）。

```bash
git fetch origin <diff_base> pull/<一番上の PR>/head
git diff --stat origin/<diff_base>...FETCH_HEAD
git diff origin/<diff_base>...FETCH_HEAD -- <path>
```

手元に無ければ `gh api repos/<owner>/<repo>/compare/<diff_base>...<一番上の headRefOid>` を使う。

- **head の SHA** を控える（stack なら一番上の PR の SHA）。ファイルへのリンクと行番号はすべてこの SHA で書く
- PR 本文・関連 issue（`closingIssuesReferences`）・関連チケットから、目的・背景・受け入れ条件を拾う
- 既存のレビューコメントで議論になっている点があれば、「重点的に見る箇所」の材料にする
- リポジトリの `CLAUDE.md`・`AGENTS.md`・`README`・`docs/`・ADR のうち、変更箇所に関係する部分だけを読む

## 3. 前提知識を調べる

この章が、コードベースを知らない人向けの資料の中心になる。**base 側（変更前）のコード**を読み、次を調べる。

- **今の機能**: 変更が関わる機能が、今どの画面で、ユーザーの何の操作で、内部のどこを通って動いているか。
  画面名・ボタン名は i18n の文言などコード上の表示名で書く
- **データモデル**: 関わるテーブル・型・API のスキーマ。カラムや項目は、この PR の理解に要るものだけに絞る
- **用語集**: ドメイン用語と、コード上の名前（クラス名・テーブル名など）の対応

書き方の決まり:

- 「今はこう動く」という説明には、根拠のファイルと行（base 側）を必ず添える。根拠が無い説明は書かない。
  推測で補うなら「推測」と明記する
- データモデルの図（mermaid の `erDiagram`）は、スキーマが変わる PR か、テーブル間の関係が分からないと変更を
  読めない PR のときだけ描く。スキーマが変わるなら変更前と変更後を並べ、増えた・変わった項目を本文で示す

## 4. 変更内容を整理し、絵にする

ファイル単位ではなく、**振る舞いの単位**で整理する。

- **TL;DR**: 3 行以内。誰の・何の課題を・どう変えるか
- **変更前と変更後**: ユーザーから見える振る舞い・内部の振る舞いを比較表にする
- **スキーマ・API・設定の差分**: migration、API の入出力、設定値、feature flag、権限。無ければ「なし」と書く
- **重点的に見る箇所**: 互換性、データ移行、境界条件、権限、PR 本文に書かれていない副作用など、レビュアーが
  時間をかけるべき場所。評価はせず、なぜ見るべきかを事実で書く
- **未確認事項**: 調べきれなかったこと、監視モードから呼ばれたときに置いた仮定

### 絵で見る

資料の冒頭（TL;DR の直後）に、**文章を読まなくても絵だけで「何が・どこで・どう変わるか」がつかめる**章を置く。
コードベースを何も知らない人に説明するつもりで、大きな絵と少ない言葉で描く。

何を描くか（2〜4 枚。1 枚で 1 つの問いに答える）:

| 絵                       | 答える問い                                   | 描くとき                                       |
| ------------------------ | -------------------------------------------- | ---------------------------------------------- |
| **この PR は何をする？** | 変更前と変更後で、ユーザーや処理がどう変わる | 必ず描く。左に変更前、右に変更後を並べる       |
| **どこを触る？**         | 画面・共通処理・API・データのどこが変わるか  | 変更が 2 つ以上の層・機能にまたがるとき        |
| **データはどう流れる？** | 値がどこで作られ、どこを通って、どこに残るか | データの形や流れが変わるとき                   |
| **状態はどう変わる？**   | 状態の種類と、どの操作でどこへ移るか         | 状態（ステータス・フラグ）が増える・変わるとき |

描き方:

- **inline SVG** で描き、雛形の図の部品（`.dg` の class）を使う。`box`（箱）、`box changed`（変わる）、`box added`（増える）、
  `box removed`（なくなる）、`zone`（まとまりの点線枠）、`edge`（矢印。`changed` / `added` / `removed` も付けられる）、
  `text.title` / `text.small` / `text.icon`（絵文字のアイコン）、`badge`（番号の丸）。色は class が theme に合わせて付けるので、
  `fill` や `stroke` を直接書かない
- 矢印の先は `marker-end="url(#arrow)"`。`<marker id="arrow">` は雛形の 1 枚目の SVG にあるので、2 枚目以降で定義し直さない
- **箱の名前は、知らない人にも分かる言葉**（画面名・機能名・役割）で書く。クラス名・ファイル名は `text.small` の補足に回す
- **色を付けるのは変わるところだけ**。変わらない箱は色を付けない。色の意味は章の先頭の凡例で示す
- 1 枚の箱は 8 個までを目安にする。多いときはまとまりを `zone` でくくるか、絵を分ける
- 「どこを触る？」の絵では、変更グループの番号（5 で振る順番）を `badge` で箱に付け、グループとの対応を示す
- 絵の中身にも 3 と同じく根拠が要る。推測で描いた箱や矢印があれば、`figcaption` に「推測」と書く
- 横幅は `viewBox` で決め、`width` / `height` は書かない（スマホでも縮んで収まる）。横長の絵は `class="picture wide"` にする
  （狭い画面ではカードの中で横にスクロールする）

### シーケンス図は必要な場合のみ描く

シーケンス図は、**本文だけでは順序や関係が追えない難しいやりとり**があるときだけ描く。目安:

- 3 者以上（画面・API・ジョブ・外部サービスなど）が絡み、呼ぶ順番が結果を左右する
- 非同期処理・リトライ・コールバック・状態遷移があり、どこで何が起きるかが分かりにくい

画面 → API → DB の素直な一往復なら描かない。描くときも、難しい部分だけに絞り、変わった箇所を `Note` などで示す。

## 5. 差分を変更グループに分け、解説を付ける

差分全体を、**意図ごとの変更グループ**に分ける。レビュアーはグループ単位で「意図 → 差分」の順に読み、読み終えたら
「確認済み」を付ける（HTML 上でチェックすると進捗バーが進み、ブラウザに保存される）。差分の HTML はスクリプトが作るので、
エージェントは振り分けと解説だけを書く。

1. **hunk に分ける**。2 で取った差分（stack なら全体の差分）を渡す

   ```bash
   git diff origin/<base>...FETCH_HEAD | python3 <この skill のディレクトリ>/scripts/split_hunks.py \
     --out <作業ディレクトリ>/hunks.json --index
   ```

   `--index` で hunk ごとに 1 行の一覧（`h001 path @@ -1,10 +1,13 @@ +3 -2 | 最初の変更行`）が出る。振り分けはこの
   一覧と、必要に応じて実際のコードを読んで行う

2. **groups.json を書く**。書式は `scripts/render_groups.py` の冒頭を参照
   - グループは「同じ意図で、一緒に読むと分かる変更」の単位。ファイル単位ではない。1 つのファイルの hunk が複数の
     グループに分かれてよい
   - **読む順に並べる**: 土台（共通基盤・型・スキーマ）→ それを使う側 → 周辺 → テスト・ドキュメント。並べた順に
     1, 2, 3… の番号が付き、一覧・詳細・「どこを触る？」の絵の `badge` で共通に使う
   - `title` は何をする変更かが分かる名前、`summary` は一覧に出す 1 文、`intent` は**なぜ**この変更をするのか
   - `risk` は壊れたときの影響範囲と、変更の難しさで決める
     - `high`（要注意）: 多くの画面・機能が通る共通処理、認証・権限、データ移行、互換性が切れる変更
     - `medium`（注意）: 振る舞いが変わるが影響が局所的、置き換えが機械的だが量が多い
     - `low`（低リスク）: ドキュメント、テストだけ、振る舞いの変わらない整理
   - `checkpoints` には、そのグループでレビュアーが確かめるべきことを書く（「legacy-path でも URL が変わらないか」など）。
     評価ではなく確認の観点として書く。無ければ省く
   - `hunk_notes` は、hunk 単体では意図が読めないところにだけ付ける
   - lockfile・生成物・スナップショットは `kind: "generated"` のグループにまとめる（折りたたんで最後に出る）
   - stack なら `prs` にどの PR の変更かを入れる（各 PR の `files` と突き合わせる）
   - **すべての hunk をちょうど 1 つのグループに入れる**。漏れや重複があるとスクリプトが止まるので、直して再実行する

3. **HTML に差し込む**のは 7 で行う

## 6. 動作確認手順を書く

ユーザーがそのまま手を動かせる粒度で、**URL と操作を 1 つずつ**書き下す。

- **環境**: 基本はローカル（localhost）。PR の head への切り替え、起動コマンド、ポート、必要な設定を書く。PR に
  Preview 環境があれば、その URL も併記する。stack なら一番上の PR の head で確かめる
- **前提**: feature flag、権限・ロール、必要なデータ、アカウント
- **不具合修正なら**、修正前の環境で不具合を再現する手順を先に置く
- **各手順**: 開く URL → 操作（押すボタンの表示名、入力値）→ 期待結果（画面の表示、メッセージの文言、Network タブで
  見る API とステータス）。ボタンが押せる条件（例: 変更が無いと保存が無効）もコードで確かめて書く
- **破壊的な操作**（削除など）には、テスト用のデータで行うよう注意を添える
- 1 つの手順は 1 つの確認に対応させ、手順ごとに `id`（`step-1` など）を振る。スクリーンショットとの対応に使う

### スクリーンショットを撮る（頼まれたときだけ）

ユーザーが「スクショも撮って」などと頼んだときだけ撮る。

1. **撮る先の URL を決める**。ユーザーが URL を伝えていればそれを使う。無ければ次の順で決める
   - **localhost（多くはこちら）**: 手元で PR の head のアプリが起動していれば、その URL（`http://localhost:<port>`）を使う。
     起動していなければ、6 の「環境」に書いた手順（PR の head への切り替え、起動コマンド）で起動してよいかユーザーに聞く。
     起動コマンドはリポジトリの README・`package.json` の scripts・mise の task などで確かめる
   - **Preview**: PR のコメント（Vercel などの bot）と `gh api repos/<owner>/<repo>/deployments?sha=<head SHA>` → 各
     deployment の statuses の `environment_url` から探す
   - どちらも決まらなければユーザーに聞く。監視モードから呼ばれたときは撮らずに「未確認事項」に書く
2. **撮影計画の JSON を書く**。動作確認手順の各手順を、URL と操作に落とす。書式は `scripts/screenshot.py` の冒頭を参照

   ```json
   {
     "base_url": "http://localhost:3000",
     "shots": [
       {
         "id": "step-1",
         "url": "/settings/profile",
         "actions": [
           { "type": "click", "selector": "role=button[name='編集']" },
           { "type": "wait_for", "selector": "text=プロフィールを編集" }
         ],
         "capture": { "selector": "main" },
         "mask": ["[data-testid='email']"]
       }
     ]
   }
   ```

3. **撮る**

   ```bash
   uv run <この skill のディレクトリ>/scripts/screenshot.py --plan <作業ディレクトリ>/shots.json \
     --out-dir <作業ディレクトリ>/screenshots
   ```

   結果は `<作業ディレクトリ>/screenshots/manifest.json` に、手順ごとの画像のパスと成否が出る。失敗した手順は、エラーを
   手順の下に書いて画像なしで載せる（撮り直しは 1 回まで）

## 7. HTML を書き出す

`assets/skeleton.html` をコピーし、各 section を埋める。雛形のコメントに、各 section で書くことがある。
書くことが無い section（stack でない PR の「スタック構成」、図が要らないときの図など）は丸ごと消す。

- **出力先**: カレントディレクトリの `./plan/<名前>.html`（`./plan` が無ければ作る）。`<名前>` は単体の PR なら
  `pr-<N>`、stack なら `stack-<stack 番号>`
- **作業ディレクトリ**: `hunks.json`・`groups.json`・スクリーンショットなどの途中のファイルは
  `./plan/.pr-reviewer-brief/<名前>/` に置く
- `<meta name="pr-reviewer-brief-head">` に head の SHA（stack なら一番上の PR の SHA）を入れる。定期実行で作り直しの要否を判断するのに使う
- ER 図とシーケンス図は mermaid で書く（雛形が読み込む）。それ以外の図は「絵で見る」と同じく inline SVG で描く
- 他の section を埋めたあとで、変更グループを差し込む。グループの一覧（変更量のバー付き）・変更ファイルの地図
  （ディレクトリごとのファイルと変更量、どのグループに入っているか）・グループごとの差分が入る。ヘッダーのファイル数・
  hunk 数・確認の進捗も、差し込んだグループから自動で埋まる

  ```bash
  python3 <この skill のディレクトリ>/scripts/render_groups.py --hunks <作業ディレクトリ>/hunks.json \
    --groups <作業ディレクトリ>/groups.json --html ./plan/<名前>.html \
    --blob-url https://github.com/<owner>/<repo>/blob/<head SHA>
  ```

- 最後に、スクリーンショットを HTML に埋め込み、1 ファイルで共有できるようにする（撮らなかったときは不要）。
  埋め込む前の `<img>` は、HTML から見た相対パス `.pr-reviewer-brief/<名前>/screenshots/<id>.png` で書いておく

  ```bash
  python3 <この skill のディレクトリ>/scripts/embed_images.py ./plan/<名前>.html
  ```

書き出したら、ファイルのパスを伝え、ターミナルにも TL;DR、（stack なら）スタック構成の表、変更グループの一覧
（タイトル・リスク・hunk 数）を出す。
Claude Code で Artifact として公開できる環境なら、ユーザーに確認したうえで公開してよい。

## 監視モード（`--watch`）

新しく作られた PR を監視し、PR ごとに最初の 1 回だけ資料を自動で作る。作り直しはユーザーが手で行う。Claude Code 専用（バックグラウンドのコマンドと
subagent を使う）。ユーザーは対象リポジトリで Claude Code を立ち上げっぱなしにしておく（tmux の中など）。
このセッション（メイン）は監視と依頼だけをするので、軽いモデル（`claude --model haiku`）でよい。

**トークンを抑えるため、次を守る**

- 待っている間はモデルを動かさない。監視はスクリプトが `gh` を叩くだけで行い、対象が見つかるまで終了しない
- 資料作りは毎回 subagent に任せ、メインの会話にコードや差分を読み込まない。メインの返答は各回 1〜2 行にする
- 作るのは 1 件ずつ順番に

### 手順

1. **監視を始める**。Bash の `run_in_background: true` で起動し、終わるまで何もせず待つ（ポーリングしない。
   終わると通知で起こされる）。Bash の timeout は `--max-wait` より長くする

   ```bash
   python3 <この skill のディレクトリ>/scripts/watch_prs.py
   ```

   既定では、平日 9〜20 時に 10 分ごと確認し、対象が無いまま 110 分経つと空の結果で終わる。ユーザーが間隔や
   時間帯を指定したら `--interval`・`--hours`・`--weekdays` で渡す（意味はスクリプトの冒頭を参照）。対象の条件:
   - カレントディレクトリのリポジトリの open な PR のうち、まだ見ていないもの（draft と自分が作ったものは除く）
   - gh stack の stack は stack 単位で 1 件にまとめ、stack ごとに 1 回だけ出す
   - 初めて起動したときに open だった PR は対象にしない（監視を始めたあとに作られた PR だけ）

2. **結果を読む**。標準出力の最後の 1 行が JSON。
   - `targets` の各件について、**1 件ずつ** Agent ツールで subagent を起動する（`model: "sonnet"`、フォアグラウンド）。
     プロンプトは次のとおり

     > `<この skill のディレクトリ>/SKILL.md` を読み、その手順で `<arg>` の資料を作ってください。監視モードから
     > 呼ばれているので「監視モードから呼ばれたとき」のルールに従ってください。最後に、出力した HTML のパスだけを返してください。

     終わったら通知する。失敗したら失敗を通知し、作り直しはしない（ユーザーが手で `/pr-reviewer-brief <arg>` を実行する）

     ```bash
     python3 <この skill のディレクトリ>/scripts/watch_prs.py --notify "<arg> の資料: <HTML のパス>"
     ```

3. **1 に戻る**。ユーザーが止めるまで繰り返す

## 監視モードから呼ばれたとき

- ユーザーに質問しない。決められないことは仮定を置いて進め、仮定を「未確認事項」に書く
- 出力先に同じ名前の HTML があり、`pr-reviewer-brief-head` が今の head の SHA と同じなら、何もせず終了する
- スクリーンショットを頼まれていても、起動済みの localhost か Preview の URL が無ければ撮らない（アプリを起動しない）
- 終わったら、出力したファイルのパスを 1 行だけ出す

## してはいけないこと

- GitHub へ投稿しない（コメント・レビュー・ラベル・状態の変更を含む）。他人のブランチへ commit / push しない
- コードを編集しない（調べるための読み取り・テスト実行は可）
- 根拠のない「今はこう動く」を書かない
