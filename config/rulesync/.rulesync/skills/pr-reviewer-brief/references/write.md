# 段階 2: 解説を書き、HTML を作る

pr-reviewer-brief skill の段階 2。段階 1 が集めた `<作業ディレクトリ>`（以下 `<work>`）の材料から、資料の中身を
**JSON で**書く。HTML・図の座標・差分の表はスクリプトが作るので、HTML や SVG は書かない。

入力: `<work>` の `target.json`・`pr-<N>.json`・`hunks.json`・`hunks-index.txt`・`groups.json`（下書き）・`notes.md`・
`shas.json`、あれば `ticket.json`。`hunks.json` は検査と HTML の生成に使うので、消したり書き換えたりしない。`brief.json` の `base_sha`・`head_sha` は
省けば `shas.json` の値が使われる。コードは
`notes.md` が挙げた場所から読み、必要な分だけ広げる（`diff.patch` は全部読まず、要る hunk だけ見る）。

出力: `<work>/brief.json`（書式は `<skill>/scripts/render_brief.py` の冒頭）と、仕上げた `<work>/groups.json`。

この skill は**説明に徹する**。良し悪しの指摘はしない（気づいた懸念は「重点的に見る箇所」に事実として書く）。

`target.json` に `"mode": "ticket"` があればチケットモード。下の「チケットモードのとき」も読む。

`prs`・`related_prs` の `url` は取得した PR の URL を必ず転記する。`stack.url` は `target.json` の
`stack_url` を転記する。本文で PR 番号やチケット ID に言及するときも `[#123](https://...)` のようなリンクにする。

## 1. 前提知識（`background`）

資料の中心。**変更前（base 側）のコード**を読み、コードベースを知らない人向けに書く。

- `ticket.json` があれば、前提知識の先頭に「チケットの内容」として自動で出る（`brief.json` に書かなくてよい）。チケットの
  目的・やること・受け入れ条件は、`tldr`・`current`・変更前後の比較を書く材料にする。チケットに書かれたことと PR の変更が
  食い違えば、PR モードでは `focus` に、チケットモードでは `changes.before_after` にその事実を書く

読み手は「既存の Web ページの**どの画面の・どこ**の話か」が分からないと追えない。前提知識は画面を起点に書く。

- `pages`（関係する画面）: 変更が関わる画面をすべて挙げる。`id`（ほかの項目から指す短い名前）、`name`（画面のタイトルや
  メニューの表示名）、`url`（ルーティングの定義から。`/approaches/:id` のようにパスで）、`looks`（**見た目**: レイアウトと
  主な部品を 1〜2 文。「上に検索フォーム、下に土地カードが縦に並ぶ」のように画面を見たことが無い人に伝わる言葉で）、
  `evidence`（ルーティングやページのファイル）。画面の無い変更（バッチ・API だけ）なら省く
- `current`: 変更が関わる機能が、今ユーザーの何の操作で、内部のどこを通って動いているか。`page`（`pages` の id）と
  `where`（その画面の**どこ**か。「各土地カードの下部」「右上の保存ボタン」のように見た目の言葉で）を付ける。
  画面名・ボタン名は i18n の文言などコード上の表示名で書く。**各項目に根拠（`evidence` のファイルと行）を必ず付ける**。
  根拠が無い説明は書かない。推測で補うなら「推測」と書く
- `glossary`: ドメイン用語と、コード上の名前（クラス名・テーブル名など）の対応。画面に出る用語には `page` と `where`
  （画面のどこに、どんな見た目で出るか。「カード右上の色付きラベル」など）を付ける
- `data_model`: **今回の変更に関わるテーブルの構造**と、画面に出ているデータが**どのテーブルから来て、テーブル同士が
  どうつながるか**を示す。変更が DB のデータ（読み書き・migration・モデル）に触れる、または画面に DB のデータが出るなら必ず書く
  - `tables`: 変更で読み書きするテーブル、migration やモデルが変わるテーブル、画面に出るデータの元のテーブルを、
    mermaid `erDiagram` で書く。各テーブルに PK / FK・型・変更に関わるカラム・画面に出るカラムを載せ、リレーション
    （多重度）でつなぐ（モデル・スキーマの定義から。関係しないテーブルは描かない）
  - `mapping`: 画面の項目とテーブルのカラムの対応（`page`・`ui`・`column`）。集計なら `count(approaches.id)` のように書く
  - スキーマが変わる PR なら、`before` と `after` も書き、増えた・変わった項目を `note` で示す
  - **画像（スクリーンショット）に映る内容は、どのテーブルのレコードか分かるようにする**。`pages[]` と `manual_test.steps[]` に
    `records` を書く（画像の下に出る）。1 件ごとに `ui`（画像に映る項目）・`table`・`record`（どの行か。`seed` で入れた行なら
    その ID や名前）・`column` を書く。画像を撮らない場合も、`mapping` で画面の項目とカラムの対応を書く

## 2. 変更内容

ファイル単位ではなく、**振る舞いの単位**で整理する。

- `tldr`: 3 行以内。誰の・何の課題を・どう変えるか。専門用語は使わない
- `scope`（変更の範囲）: 画面（`fe`）・サーバー（`be`）・データベース（`db`）・インフラ（`infra`）のどこが、どう変わるかの
  概略。各層に次を書く。ファイル数・行数・変更グループの番号は、`paths` で差分のファイルを振り分けてスクリプトが数える
  - `summary`: その層で何が変わるか 1 文（変わらない層は「migration なし」など変わらないことを書く）
  - `paths`: その層のファイルが置かれるディレクトリ（リポジトリのルートからのパスの先頭。例: `web/src/`、`api/`）
  - `parts`: 層の中の部品を 1〜5 個。変わる部品と、読むのに要る変わらない部品だけ。それぞれ `name`（知らない人にも分かる名前）、
    `detail`（画面なら URL、API ならエンドポイント `GET /approaches`、インフラならリソース名やワークフロー名）、`paths`、
    `summary`（その部品で何が変わるか 1 文）を書く。部品の目安:
    - 画面: ページ（画面ごと）・共通コンポーネント・状態管理 / API クライアント
    - サーバー: API（エンドポイントのまとまり）・ドメイン / ユースケース・モデル・バッチ / ジョブ・外部連携
    - データベース: migration・スキーマ / 初期データ
    - インフラ: IaC（Terraform など）・CI / CD・Docker / 実行環境・環境変数 / 設定
  - どの部品にも当たらない層のファイルは層の「その他」、どの層の `paths` にも当たらないファイル（docs など）は全体の
    「その他」に入る
- `changes.before_after`: ユーザーから見える振る舞い・内部の振る舞いの比較表。画面に出る変化には `page` と `where`
  （どの画面の・どの項目か）を付ける
- `changes.sequences`: **本文だけでは順序や関係が追えない難しいやりとり**があるときだけ、mermaid の `sequenceDiagram` を書く。
  3 者以上が絡み呼ぶ順番が結果を左右する、非同期・リトライ・コールバック・状態遷移がある、などが目安。画面 → API → DB の
  素直な一往復なら書かない。書くときも難しい部分だけに絞り、変わった箇所を `Note` で示す
- `interfaces`: migration、API の入出力、設定値、feature flag、権限の差分。無ければ空の配列（「なし」と出る）
- `focus`: 互換性、データ移行、境界条件、権限、PR 本文に書かれていない副作用など、レビュアーが時間をかけるべき場所と理由
- `unknowns`: 調べきれなかったこと、置いた仮定

## 3. 絵で見る（`pictures`）

文章を読まなくても絵だけで「何が・どこで・どう変わるか」がつかめるようにする。コードベースを何も知らない人に
説明するつもりで、大きな絵と少ない言葉で。**絵の中身（何を描くか）だけを JSON で指定する**。書式と例は
`<skill>/scripts/render_pictures.py` の冒頭。

| 絵（type）                           | 答える問い                                     | 描くとき                                       |
| ------------------------------------ | ---------------------------------------------- | ---------------------------------------------- |
| この PR は何をする？（before_after） | 変更前と変更後で、ユーザーや処理がどう変わるか | 必ず描く                                       |
| データはどう流れる？（flow）         | 値がどこで作られ、どこを通って、どこに残るか   | データの形や流れが変わるとき                   |
| 状態はどう変わる？（flow）           | 状態の種類と、どの操作でどこへ移るか           | 状態（ステータス・フラグ）が増える・変わるとき |

- 1〜3 枚。1 枚で 1 つの問いに答える。どこ（画面・サーバー・データベース）を触るかは絵ではなく `scope`（2 の変更の範囲）で示す。箱は 1 枚 8 個までを目安にし、多ければ絵を分ける
- **ラベルは短く**: 箱の `label` は 12 文字前後まで（長ければ `\n` で 2 行に）、矢印の `label` は 6 文字前後まで。
  説明が要るなら `lead` や `caption` に書く（ラベルは折り返されないので、長いと絵が横に広がって文字が小さくなる）
- **箱の名前は知らない人にも分かる言葉**（画面名・機能名・役割）。クラス名・ファイル名は `sub` に回す
- **`status` を付けるのは変わるところだけ**（changed / added / removed）。変わらない箱には付けない
- 絵にも 1 と同じく根拠が要る。描いた箱や矢印の根拠のファイルと行を `caption` に書く（例: 「根拠: `app/x.ts:10-20`」）。
  推測で描いた部分があれば、それも `caption` に「推測」と書く

## 4. 変更グループを仕上げる

下書きの `groups.json` の各グループに、次を足す。`title` や並び順は直してよいが、**hunk の振り分けは崩さない**
（直すなら、すべての hunk がちょうど 1 グループに入ったままにする）。

- `summary`: 一覧に出す 1 文
- `intent`: **なぜ**この変更をするのか
- `risk`: 壊れたときの影響範囲と、変更の難しさで決める
  - `high`（要注意）: 多くの画面・機能が通る共通処理、認証・権限、データ移行、互換性が切れる変更
  - `medium`（注意）: 振る舞いが変わるが影響が局所的、置き換えが機械的だが量が多い
  - `low`（低リスク）: ドキュメント、テストだけ、振る舞いの変わらない整理
- `impact`（任意）: 影響範囲
- `checkpoints`（任意）: そのグループでレビュアーが確かめること（「legacy-path でも URL が変わらないか」など）。
  評価ではなく確認の観点として書く
- `hunk_notes`（任意）: hunk 単体では意図が読めないところにだけ付ける

## 5. 動作確認手順（`manual_test`）

画面のある変更は、レビュアーが**ブラウザの画面を操作して**確かめる手順にする（画面の無い変更は下の `steps` のとおり）。データを用意するところから、そのまま手を動かせる粒度で書く。

- `environment`: 基本はローカル（localhost）。PR の head への切り替え、起動コマンド、ポート、必要な設定。PR に Preview 環境が
  あれば、その URL も書く。stack なら一番上の PR の head で確かめる
- `preconditions`: feature flag、権限・ロール、ログインするアカウント
- `seed`（テストデータ）: 手順に要るデータを入れるスクリプト。画面だけでは用意できないデータ（別のユーザーの記録、過去の日付、
  件数の多いデータなど）があれば必ず書く
  - **標準 SQL で準備できるようにする**。`language` は `sql`、`script` はカラムを明示した `INSERT INTO ... VALUES ...` を
    基本とし、ORM・factory・アプリの seed コマンドへの依存を避ける。既存の seed や factory は必要な値を調べる参考にする。
    カラム名・型・必須項目・外部キーをモデル・migration で確認し、参照される親レコードから順に作る
  - DB 固有の構文（`ON CONFLICT`、`INSERT IGNORE`、`RETURNING`、`::` キャストなど）、CLI のメタコマンド、
    アプリ側の変数展開は SQL 本体に含めない。固定の ID・日時・文字列で、そのまま実行できる SQL にする（ID は自動採番と衝突しない大きな値を選ぶ）。
    固有機能やアプリ側の生成処理が不可欠なら、必要な理由と追加の準備を `note`・`preconditions` に明記する
  - `run` に対象 DB と、SQL クライアントでその DB に接続し、下の SQL をクエリエディタに貼り付けて直接実行する手順を記載する。
    SQL ファイルの保存や `psql`・`mysql` などの CLI コマンドによる実行は前提にしない。
    `cleanup` も標準 SQL の `DELETE` とし、事前に未使用と確認したテスト専用の固定 ID で今回入れた行だけを対象にし、投入に失敗した場合は実行せず、子レコードから順に消す
  - 手順で使う値（ID・名前）はスクリプトで固定し、手順の中でもその値を使う（「名前が `test-land-1` の土地カード」など）
- `steps`: 1 つの手順は 1 つの確認。`id` は `step-1` から順に振る（スクリーンショットとの対応に使う）
  - 画面のある変更（`background.pages` がある）は**画面の操作だけで書く**。API を直接呼ぶ・DB を見るといった確かめ方は
    書かない（必要なら `expected` の補足に回す）。画面の無い変更（API・バッチだけ）は、API の呼び出し・ジョブの実行・
    DB の確認など、実際に確かめられる手段で同じように 1 つずつ書く（`actions` にコマンド、`expected` にレスポンスや結果）
  - `url`: 開く画面の URL（`seed` で入れた ID を埋めた、そのまま開ける URL）。画面の無い手順では省く
  - `actions`: 操作を 1 つずつ配列で、画面の表示名で書く。「どこの・何を・どうする」がそろうように書く
    （例: 「右上の『新規作成』ボタンを押す」「『名前』の欄に `test` と入力する」「一覧の 2 行目の『編集』を押す」）
  - `expected`: 操作のあとに**画面で見えるもの**を配列で（表示される文言、増える行、色やラベルの変化、出るメッセージ）。
    画面の無い手順では、レスポンス・ジョブの出力・DB の値など確かめられる結果を書く
  - 不具合修正なら、修正前の環境で不具合を再現する手順を先に置く
  - ボタンが押せる条件（例: 変更が無いと保存が無効）もコードで確かめて書く
  - 削除など元に戻せない操作には `caution` で、テスト用のデータで行うよう注意を添える

## 6. HTML を作り、確かめる

`page` に書いた id が `background.pages` に無いと、`render_brief.py` がエラーにする。

チケットモードでは 1 行目（`render_groups.py`）を飛ばす。

```bash
python3 <skill>/scripts/render_groups.py --hunks <work>/hunks.json --groups <work>/groups.json --check full
python3 <skill>/scripts/render_brief.py --workdir <work> --out <出力先の HTML>
```

エラーが出たら `brief.json`・`groups.json` を直して再実行する。出力先は依頼のときに渡される。

## チケットモードのとき

PR ではなくチケットを渡されたとき。資料には **TL;DR・スタック構成・前提知識・変更内容だけ**が出る（それ以外は書いても
出ない）。チケットの内容と、それを理解するための前提知識をつかむための資料にする。

- `brief.json` に `"mode": "ticket"` を入れる。`title` はチケットのタイトルにする（取れなかったときはチケットの ID）
- `tldr`: このチケットで、誰の・何の課題を・どう変えるのか。チケットの中身が取れなかったときは、そのことと、PR やコードから
  分かったことを書く
- `background`: 1 と同じ。チケットに出てくる画面・機能が**今**どう動いているかを、今の default branch のコードを読んで根拠付きで書く
- 変更内容: 関連する PR があれば、`target.json` と各 `pr-<N>.json` から
  `brief.json` の `prs`（書式は `render_brief.py` の冒頭。`changedFiles` は `files` に、`baseRefName`・`headRefName` は
  `base`・`head` にする）と、stack なら `stack`（`{"number": <stack_number>, "trunk": <trunk>, "url": <stack_url>}`）を書き、
  `changes.before_after` を書く。PR ごとの 1 文のまとめは、stack の PR なら `prs[].summary`（スタック構成に出る）、
  それ以外の PR なら `related_prs` に書く。PR が無ければ、チケットに書かれた
  「これから変えること」を `changes.before_after` にまとめる（変更後の列は「チケットでの予定」と分かるように書く）
- 変更グループ・絵・動作確認手順・重点的に見る箇所は書かない。`render_groups.py` の検査もしない

## 終わり方

最後に 1 行だけ返す: 出力した HTML のパス。
