# 指摘候補の洗い出しと出し方

pr-reviewer-comment / pr-reviewer-comment-crit skill の共通手順。

agent-lessons が設定済み（`basic-memory tool list-projects` に `agent-lessons` がある）なら、読む前に過去の指摘から
観点を引いておく。自分がよく書く指摘（`given`）とチームの規約（`team`）が対象。ここで引いた観点も、下の裏取りを通してから候補にする。

```bash
filter=$(jq -cn --argjson keys "$(agent-lessons-context --scope-keys)" \
  '{scope_key: {"$in": $keys}, source: {"$in": ["given", "team"]}}')
basic-memory tool search-notes --type lesson --status active --filter "$filter" \
  --project agent-lessons --page-size 50 --json
```

diff だけを読まない。変更した関数の呼び出し元・呼び出し先、同じデータを読む別の経路（取得と保存、新旧の API など）、追加されたテストまで読む。`/code-review` を併用してよいが、その出力は**候補**として扱い、下の裏取りを通す。

**候補として出す前に（表にも crit にも）、1 件ずつ裏を取る。** 誤った指摘を作成者に送ると、作成者の時間を奪い、レビュー全体の信頼も下がるため。

- 「〜が無い」と書く前に、diff 全体（**ファイル末尾に追加されたテスト**を含む）と既存コードを grep し、本当に無いことを確かめる
- 「〜になる」と書く前に、その分岐が実際に踏まれる条件をコードで追う。追い切れないものは「可能性」と書くか、区分を Q にする
- 行番号は推測しない。head の SHA のファイルを `git show <sha>:<path> | nl -ba | sed -n '<from>,<to>p'` で表示して数える
- PR 本文やコードコメントで作成者が既に認めている事柄なら、それを指摘の根拠として引用する

裏取りで成り立たなかった候補は捨てずに控えておく。submit 本文の「コード観点」に「〜は確認の結果、成り立たない」と書く材料になる。

## 区分

| 区分   | 意味                                                                        |
| ------ | --------------------------------------------------------------------------- |
| must   | マージを止める欠陥。データ破損・セキュリティ・要件未達など                  |
| should | 直してほしい。PR の目的や不変条件を損なう、テストが変更を守っていない、など |
| imo    | 意見・設計の好み。直さなくても動く                                          |
| nit    | 体裁・命名・重複など、実害の無いもの                                        |
| Q      | 質問。意図の確認や、裏が取り切れない懸念                                    |

must が 0 件のことは普通にある。無理に上げない。区分に迷ったら、両方の見方を「区分理由」に書いてユーザーに委ねる。

## 本 PR との関係（◯ / △ / ☓）

| 記号 | 意味                                                                                           |
| ---- | ---------------------------------------------------------------------------------------------- |
| ◯    | この PR が追加・変更した行への指摘                                                             |
| △    | 既存のコードだが、この PR の変更の効果・前提・不変条件を損なう（直さないと PR の目的が欠ける） |
| ☓    | この PR が触っていない既存のコード。同じ根の問題や、範囲を超えるリファクタ                     |

記号には必ず理由を 1 行添える（例: 「△ 処理自体は既存だが、PR が足した整合性の保証が同時実行で崩れる」）。☓ の指摘は「別チケットで」と添えて出すかどうかをユーザーが決める。

## 出し方

### 表

```markdown
| No  | 区分   | 一言                           | 本PRとの関係                                                    | 区分理由                         | 対象コード                       |
| --- | ------ | ------------------------------ | --------------------------------------------------------------- | -------------------------------- | -------------------------------- |
| 1   | should | 更新処理がロックを取っていない | △ 処理自体は既存だが、PR が足した整合性の保証が同時実行で崩れる | PR の目的が欠ける。直すのは 1 行 | `app/usecases/orders.py:120-128` |
```

並び順は区分の重い順（must → should → imo → nit → Q）。

### 詳細（No ごと）

````markdown
### No.1 [should] <一言>

**理由**: <なぜ問題か。起きる条件と、起きたときの結果>

**対象コード**: `path/to/file.py:120-128`

```python
<head の SHA のコードをそのまま貼る>
```

**関連コード**: `path/to/other.py:45`（<何との比較か>）

```python
<コード>
```
````

関連コードが無ければ「関連コード」の項は省く。コードは要約せず、行番号どおりに貼る。
