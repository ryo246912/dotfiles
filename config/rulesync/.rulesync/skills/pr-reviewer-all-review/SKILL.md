## ヘルプ・引数

`-h` / `--help` があれば、他の引数より優先して使い方・オプション・既定動作を表示し、PR の取得や投稿を行わず終了する。不明なオプションでも処理を開始せず、このヘルプを表示する。

Claude Code は `/pr-reviewer-all-review`、Codex は `$pr-reviewer-all-review` に PR の URL または番号を渡す。

| 引数                   | 意味                                                                                                      |
| ---------------------- | --------------------------------------------------------------------------------------------------------- |
| `-h`, `--help`         | ヘルプのみ表示して終了                                                                                    |
| `-s`, `--select`       | 実行するレビューと crit・brief・behavior を開始前に選ぶ                                                   |
| `-c`, `--crit`         | crit で候補を確認                                                                                         |
| `-br`, `--brief`       | PR の解説資料を作る                                                                                       |
| `-nb`, `--no-behavior` | 実環境での動作確認を省略                                                                                  |
| `--submit`             | 選ばれた指摘を再確認なしで公開。種別を指定する場合は `--submit APPROVE` または `--submit REQUEST_CHANGES` |

`-s`、`-c`、`-br`、`-nb` は対応する長いオプションと同じ指定として扱う。同じ指定が重複しても対応する段階は一度だけ実行する。

既定では指摘候補の提示後に選択を待ち、選んだ指摘を draft にする。開始時の `--submit` と、候補提示後の `submit`は同じ公開指定として扱う。

# pr-reviewer-all-review — PR レビューの開始から draft または公開まで

レビュアーとして他人の PR を読み、**指摘候補を出す → ユーザーが選ぶ → draft を作るか公開する**までを進める。
ユーザーがレビューの公開指示に `submit` を使った場合（`submit` 単独や開始時の `--submit` も含む）は、投稿する No が決まり次第、追加の文面確認を挟まず公開する。通常は draft と本文例を作る。

## レビュー段階と責務

[レビュアー向けの段階一覧](references/stages.md) と、**[作者向けの段階一覧](../pr-author-all-review/references/stages.md) の共通列が「レビュアー」の全行**を最初に読む。後者が段階 3 の専門スキルと適用条件の正本。必ず開き、[段階 3 の実行確認](references/stages.md#段階-3-の実行確認)に従う。対象 PR、差分、各段階の結果と未確認事項を記録する。

`--select` 付きなら、下の手順で実行内容を確定する。`--select` がなければ、従来どおり該当するレビューを実行し、crit・brief・behavior は既定動作と指定されたオプションに従う。

crit を使う場合は pr-crit の checkout・壁打ち・投稿手順を使う。確定した実行内容、PR 情報、専門レビュー一覧、公開指定の意図と種別を引き継ぎ、共通段階は一度だけ実行する。

## `--select` で開始前に選ぶ

1. 二つの段階一覧を読む。PR のマージ先と変更範囲を読み取り専用で確認し、一般レビュー、正本の専門スキル、マージ先に一致する環境別設定の追加スキルを候補として集める。同じスキルは対象と観点をまとめて 1 項目にする。各候補はスキル名と適用条件を示し、対象外と判明した項目は理由を示す。参照先を読めない場合は候補一覧が不完全であることを示す。
2. **A. レビュースキル（複数可）** と **B. 追加機能（複数可）** を、同じメッセージに番号付きのテキストで出す。二つの項目を同時に見せるため、候補数にかかわらず `AskUserQuestion` などの選択 UI は使わない。
   - A は段階一覧の順に 1 行 1 候補で、スキル名・観点・今回の適用判定（該当／対象外／未確認）を並べる。対象外・未確認の行には理由を添える。末尾に「該当するすべて」「追加レビューなし（直接レビューだけ）」を番号付きで置く。レビュー対象の固定と候補の裏取りに必要な直接確認は常に行う。
   - B は「1. crit（壁打ち UI）」「2. brief（解説資料）」「3. behavior（実環境での動作確認）」「4. なし」の順に、1 行ずつ示す。対象範囲や必要な環境が分かっていれば併記する。`-c` は 1、`-br` は 2 を初期案に含める。`-nb` は 3 だけを初期案から外す。初期案に追加機能が一つもなければ 4 を示し、実行内容は回答で確定する。
   - 選択肢は段階一覧、該当する環境別設定、上記の手順に定義されたものだけを使う。実際に表示した番号で回答例を作り、カンマ区切りと範囲指定を受け付ける（例 `A: 1-3 / B: 4`）。「該当するすべて」「追加レビューなし」「なし」は各項目で単独指定とする。表示外の番号や矛盾があれば、その項目だけを聞き直す。
3. 二つの回答が有効な内容で揃うまで、checkout、レビュー、実環境での操作、解説資料の作成、投稿を開始しない。確定したスキルと追加機能だけを各段階に適用する。選んだ項目にも既存の適用条件と前提を適用する。未選択のレビューは「選択外」と記録する。比較範囲の更新時も確定済みの選択を引き継ぐ。「該当するすべて」を選んだ場合は新しい差分で適用条件を再評価する。

## 1. PR の情報を集める

`references/pr-info.md` に従う。

## 2. 指摘候補を洗い出し、裏を取る

`references/findings.md` に従い、直接確認、利用可能な一般レビュー、変更内容に合う専門レビューを実行する。

## 3. 動作確認レポートを作る

[段階一覧の段階 5](references/stages.md) に従って `pr-behavior-review` を実行する。候補提示時の案内も段階 5 の共通手順に従う。

## 4. 指摘候補を出す

`references/findings.md` の「出し方」に従い、表と No ごとの詳細を出す。各 No に推奨対応案を添える。

候補の提示前、ユーザーの選択を受け取った時点、投稿直前に、共通手順の「指摘の根拠と鮮度を確認する」に従う。

## 5. 投稿する No を決めてもらう

表と詳細を出したら、**ここで止める**。投稿する No を選んでもらうまで、何も投稿しない。

- 「どの No を投稿しますか？ 区分や文面の相談もどうぞ」と聞く
- 公開指定を受けた時点で投稿する No が決まっていれば、そのまま 6 に進む。先に公開指定を受けた場合は、No が決まるまで指定と種別を引き継ぐ。投稿本文の再提示や「この内容で OK ですか？」といった再確認は不要
- 壁打ちで指摘が誤りと分かったら、表から外したことを明言する
- 区分や本 PR との関係を変えたら、表を出し直す。推奨対応案が変わったら、該当する No の詳細も出し直す

## 6. レビューを draft または公開として投稿する

`references/draft-review.md` に従う。

## してはいけないこと

- 公開の明示指定なしにレビューを submit しない。既存の PENDING レビューは submit しない
- 他人のブランチへの commit / push、他人のスレッドへの返信、ラベルや状態の変更をしない
- 裏を取っていない候補を表に載せない
