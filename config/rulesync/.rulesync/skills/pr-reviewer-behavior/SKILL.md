# PRの動作確認

## スコープ

- ユーザーが用意した起動済みの環境を使う。
- 環境構築、依存導入、サーバー起動、checkout、migration、feature flag変更、base側との比較は行わない。
- 実装の修正やGitHubへのコメント投稿は、別途依頼がなければ行わない。
- 最優先は、変更内容を確認できるデータと状態を用意し、実際の操作までたどり着くこと。自動操作が止まっても、手動で続けられる具体的な情報を残す。

## 入力と設定の補完

- 入力はPRのURLまたは番号。URLならそのリポジトリ、番号だけならカレントリポジトリから解決する。決まらない場合だけ確認する。
- 対象リポジトリのAGENTS.mdを読む。
- 設定は、この `SKILL.md` と同じディレクトリの `config.md` から読む。リポジトリごとの見出しの下にlocalとstaging（preview）、その下に複数のアカウント・データ準備手順を持つ。別リポジトリや別環境の認証情報・データ操作範囲を流用しない。
- 初回起動時に `config.md` がなければ、同じ場所の `config.example.md` をコピーして作る。既存ファイルを上書きしない。exampleを実際の設定で埋めない。
- `config.md` がある場合も、対象リポジトリの見出しがなければ追加する。毎回、未記入項目を調べ、リポジトリ・PR・接続済みChromeから確認できたURLや手順を補う。値を推測して埋めず、古い値と食い違う場合は更新前に確認する。
- 既存セッションで進められる場合、メール・パスワードの記入は不要。続行に必要な未記入項目だけ質問し、使わない環境や任意項目の入力を求めて止まらない。秘密値はチャットへ出さず、必要ならユーザーに `config.md` への記入かChromeでのログインを依頼する。
- 対象環境はユーザー指定を優先し、なければ接続中の対象タブと設定から判断する。複数候補が残る場合だけ確認する。
- 設定ファイルはシェルとして実行しない。認証情報・セッショントークン・個人情報をログ、HTML、スクリーンショットに含めない。
- 設定と成果物は `config/git/gitignore` で管理するglobal ignoreの対象とする。実行前に `git check-ignore` と `git ls-files` 等で未追跡かつ除外対象か確認する。global ignoreが未反映なら反映を案内し、各リポジトリの `.gitignore` や `.git/info/exclude` を変更しない。既に追跡されている場合は秘密値を書き込まず問題を伝える。
- rulesyncで配布される複数のスキルディレクトリは別々の設定になり得る。今回参照した `config.md` の絶対パスを保持し、補完と教訓の追記も必ず同じファイルへ行う。

## 1. PRとstackを特定する

1. GitHub connectorまたは利用可能なCLIでPRの本文、base/head、head SHA、差分、関連Issue、必要なコメントを読む。
2. GitHubのStacks APIやPR本文のstack一覧、明示された依存関係、リポジトリのstack管理情報を優先してstackを調べる。必要なら同じリポジトリで、対象のheadブランチをbaseにする後続PRをたどる。
3. 「一番上」は対象PRを含む依存チェーンの末端、すなわち他の変更を積み上げた最上位PRとする。更新日時やPR番号の大小で決めない。
4. stackが分岐して最上位候補が複数ある場合や、依存関係が確認できない場合は候補と根拠を示して確認する。勝手に一つを選ばない。
5. 入力されたPR、検証に使う最上位PR、両者の関係を記録する。確認項目は原則として入力PRの変更から作り、stack全体を依頼された場合は全体を対象にする。
6. 設定やデプロイ情報で検証URLを解決し、最上位PRのhead SHAに対応する環境か確認する。URLだけでは対応を証明できないため、確認できない場合はその旨を明記する。環境の切り替えが必要ならユーザーに依頼する。

## 2. 確認項目と到達条件を作る

- PR本文・Issueの期待動作と差分を対応させる。仕様の根拠と実装からの推測を分ける。
- 関連する画面、route、UI文言、権限チェック、API、既存のfixture・テスト・データ作成手順を読む。
- 各項目について「必要なロール／テナント」「必要なデータと状態」「開始URL」「そこからの操作」「期待結果」を整理する。
- 正常系を優先し、変更に直接関係する境界値・エラー状態・再読み込み後の保持などを追加する。
- 不明な仕様だけを限定して質問し、独立して進められる調査やデータ準備は続ける。

## 3. データと開始状態を用意する

1. 既存のテストデータで条件を満たせるか調べる。共有データを変更するより、識別可能な専用データを優先する。
2. 設定で許可された方法に従い、UI、既存のfixture/API/スクリプトを使って必要最小限のデータを作る。スクリプトは実行前に内容と書き込み先を確認する。
3. 直接DB更新は設定で許可され、既存の手順がある場合だけ使う。データの整合性を崩す独自SQLや、設定変更で無理に条件を満たすことは避ける。
4. 作成物に実行ごとの識別子を付け、レコードID、表示名、所属、状態、到達URLを記録する。必要な関連データも作り、実際に目的の状態になったことを確認する。
5. データを作る権限や手段がなければ、必要なデータの条件と不足事項を具体的に残す。環境構築やflag変更へ範囲を広げない。
6. 許可されたテスト環境・テストデータの範囲内で進める。外部送信、実決済、本番・共有データの破壊的変更は、既存の明示的な許可がない限り行わない。

## 4. 実ブラウザで到達・操作する

- Playwright MCPまたはClaude in Chromeを使い、AIが接続しているChromeの既存タブ・セッションで操作する。利用環境のブラウザスキル・接続手順に従う。利用する接続先と対象タブを確認し、新しい独立ブラウザやPlaywright CLIへ勝手に切り替えない。接続できない場合は接続を依頼し、独立してできる調査と手順作成を進める。
- localhostはブラウザとサーバーの実行場所によって異なる。接続できない場合は、その場所とURLを確認する。サーバーを起動し直さない。
- 設定の認証方法を使う。対話ログインやMFAが必要ならユーザーに引き継ぎ、同じセッションで再開する。
- 画面やDOM/accessibility snapshotを観測してから操作する。直接URLで開ける場合も、必要なテナントや前提状態を確認する。
- 操作後は対象の表示・URL・要素状態・API応答で待機する。固定sleepやnetworkidleだけで成功判定しない。
- 実際の操作と結果を確認する。保存なら再表示・再読み込み後も確認し、関連するconsole errorや失敗した通信を調べる。
- 確認した各項目の結果が分かるスクリーンショットを撮り、実際に閲覧して確認する。撮影可能な失敗状態も残す。認証入力画面や秘密情報は写さない。撮影・保存できない場合は、その理由を記載する。mockによる検証は実backendでの確認と区別する。
- 自動操作が難しい場合は、準備済みデータと可能な範囲の画面を残して、手動確認手順を作る。未実行の操作を成功扱いしない。

## 5. 成果物と引き継ぎ

リポジトリ直下の `.pr-reviewer-artifacts/<PR番号>/<実行識別子>/` に、`<PR番号>-<PRタイトル>.html`（例: `123-検索条件を追加.html`）と必要な証拠を保存する。入力PRの番号・タイトルを使い、stackの最上位PRはHTML本文に別記する。ファイル名の危険な文字・長さの処理、HTMLの構成と画像埋め込みは `references/report-format.md` に従う。Markdownだけで終わらず、スクリーンショットを埋め込んだHTMLを出力する。

特に次を残す。

- 入力PRと最上位PR、対象SHA、検証URL、環境との対応確認状況。
- 作成・再利用したデータのID、表示名、状態、直接開くURL。
- 手動で確認する人が使うロール、最初に開くURL、クリックする画面文言、入力例、期待結果。
- 各項目の PASS / FAIL / BLOCKED / NOT RUN、実結果と証拠。
- 失敗時の再現手順。不具合・環境不足・仕様不明を区別し、baseと比較していないためPR起因の断定はしない。

手動確認に使うデータは設定の保持方針に従う。指定がなければ今回作った専用データを残し、削除手順を記録する。既存データの変更は可能な範囲で戻す。認証情報の代わりにアカウントの別名や設定ファイル内の項目名を記載する。

## 6. 次回に活かす教訓を追記する

- 終了時（途中でBLOCKEDになった場合も）、今回のデータ準備・到達手順・ブラウザ操作から再利用できる知見を整理する。
- 実行時に参照した同じ `config.md` の末尾の「教訓」へ、日付・リポジトリ・local／staging・適用条件・有効だった手順・根拠を追記する。既存の記録は消さない。内容が重複する場合は追加しない。
- 未確認の推測、今回だけの一時URLやレコードID、パスワード・トークン・個人情報は教訓に書かない。誤った過去の教訓が判明した場合は、元の記録を残して訂正を追記する。
- 教訓は次回の調査の手掛かりとし、古い情報で仕様や操作の許可範囲を上書きしない。新たな許可を教訓として勝手に追加しない。
- 最後にHTMLへのリンクと準備済みデータ、未確認事項、設定の補完・教訓追記の有無を短く伝える。秘密値や設定全文を出力しない。
