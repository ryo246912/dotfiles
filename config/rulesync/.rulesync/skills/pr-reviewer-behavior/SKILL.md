# PRの動作確認

## スコープ

- ユーザーが用意した起動済みの環境を使う。
- 環境構築、依存導入、サーバー起動、checkout、migration、feature flag変更、base側との比較は行わない。
- 実装の修正やGitHubへのコメント投稿は、別途依頼がなければ行わない。
- 最優先は、変更内容を確認できるデータと状態を用意し、実際の操作までたどり着くこと。自動操作が止まっても、手動で続けられる具体的な情報を残す。

## 入力とローカル設定

- 入力はPRのURLまたは番号。番号だけなら現在のリポジトリやローカル設定から対象を解決する。複数候補がある場合だけ確認する。
- 対象リポジトリのAGENTS.mdを読む。
- 環境情報はリポジトリ直下の `.pr-reviewer.local.md` から読む。ユーザーがパスを指定した場合はそちらを使う。
- 設定がなければ、このスキルの `.pr-reviewer.local.example.md` を案内する。既存ファイルを上書きしない。秘密値をチャットで収集しない。
- 設定ファイルはシェルとして実行しない。認証情報・セッショントークン・個人情報をログ、レポート、スクリーンショットに含めない。
- 設定と成果物の保存先がGitのignore対象か確認する。未設定ならローカルの `.git/info/exclude` に追加するなど、秘密情報を追跡対象にしない。既に追跡されている場合はignoreでは保護できないため、秘密値を書き込まず問題を伝える。

## 1. PRとstackを特定する

1. GitHub connectorまたは利用可能なCLIでPRの本文、base/head、head SHA、差分、関連Issue、必要なコメントを読む。
2. GitHubのStacks APIやPR本文のstack一覧、明示された依存関係、リポジトリのstack管理情報を優先してstackを調べる。必要なら同じリポジトリで、対象のheadブランチをbaseにする後続PRをたどる。
3. 「一番上」は対象PRを含む依存チェーンの末端、すなわち他の変更を積み上げた最上位PRとする。更新日時やPR番号の大小で決めない。
4. stackが分岐して最上位候補が複数ある場合や、依存関係が確認できない場合は候補と根拠を示して確認する。勝手に一つを選ばない。
5. 入力されたPR、検証に使う最上位PR、両者の関係を記録する。確認項目は原則として入力PRの変更から作り、stack全体を依頼された場合は全体を対象にする。
6. ローカル設定やデプロイ情報で検証URLを解決し、最上位PRのhead SHAに対応する環境か確認する。URLだけでは対応を証明できないため、確認できない場合はその旨を明記する。環境の切り替えが必要ならユーザーに依頼する。

## 2. 確認項目と到達条件を作る

- PR本文・Issueの期待動作と差分を対応させる。仕様の根拠と実装からの推測を分ける。
- 関連する画面、route、UI文言、権限チェック、API、既存のfixture・テスト・データ作成手順を読む。
- 各項目について「必要なロール／テナント」「必要なデータと状態」「開始URL」「そこからの操作」「期待結果」を整理する。
- 正常系を優先し、変更に直接関係する境界値・エラー状態・再読み込み後の保持などを追加する。
- 不明な仕様だけを限定して質問し、独立して進められる調査やデータ準備は続ける。

## 3. データと開始状態を用意する

1. 既存のテストデータで条件を満たせるか調べる。共有データを変更するより、識別可能な専用データを優先する。
2. ローカル設定で許可された方法に従い、UI、既存のfixture/API/スクリプトを使って必要最小限のデータを作る。スクリプトは実行前に内容と書き込み先を確認する。
3. 直接DB更新はローカル設定で許可され、既存の手順がある場合だけ使う。データの整合性を崩す独自SQLや、設定変更で無理に条件を満たすことは避ける。
4. 作成物に実行ごとの識別子を付け、レコードID、表示名、所属、状態、到達URLを記録する。必要な関連データも作り、実際に目的の状態になったことを確認する。
5. データを作る権限や手段がなければ、必要なデータの条件と不足事項を具体的に残す。環境構築やflag変更へ範囲を広げない。
6. 許可されたテスト環境・テストデータの範囲内で進める。外部送信、実決済、本番・共有データの破壊的変更は、既存の明示的な許可がない限り行わない。

## 4. 実ブラウザで到達・操作する

- 利用環境のブラウザスキルに従い、ユーザー指定のブラウザがあればそれを使う。CLI環境で指定がなければ既存のPlaywright CLI等を使う。新しいテスト基盤の導入は不要。
- localhostはブラウザとサーバーの実行場所によって異なる。接続できない場合は、その場所とURLを確認する。サーバーを起動し直さない。
- ローカル設定の認証方法を使う。対話ログインやMFAが必要ならユーザーに引き継ぎ、同じセッションで再開する。
- 画面やDOM/accessibility snapshotを観測してから操作する。直接URLで開ける場合も、必要なテナントや前提状態を確認する。
- 操作後は対象の表示・URL・要素状態・API応答で待機する。固定sleepやnetworkidleだけで成功判定しない。
- 実際の操作と結果を確認する。保存なら再表示・再読み込み後も確認し、関連するconsole errorや失敗した通信を調べる。
- 見た目を判定する場合はスクリーンショットを実際に閲覧する。mockによる検証は実backendでの確認と区別する。
- 自動操作が難しい場合は、準備済みデータと可能な範囲の画面を残して、手動確認手順を作る。未実行の操作を成功扱いしない。

## 5. 成果物と引き継ぎ

リポジトリ直下の `.pr-reviewer-artifacts/<PR番号>/<実行識別子>/` に、秘密値を除いた `report.md` と必要な証拠を保存する。reportはこのスキルの `references/report-format.md` を使う。

特に次を残す。

- 入力PRと最上位PR、対象SHA、検証URL、環境との対応確認状況。
- 作成・再利用したデータのID、表示名、状態、直接開くURL。
- 手動で確認する人が使うロール、最初に開くURL、クリックする画面文言、入力例、期待結果。
- 各項目の PASS / FAIL / BLOCKED / NOT RUN、実結果と証拠。
- 失敗時の再現手順。不具合・環境不足・仕様不明を区別し、baseと比較していないためPR起因の断定はしない。

手動確認に使うデータはローカル設定の保持方針に従う。指定がなければ今回作った専用データを残し、削除手順を記録する。既存データの変更は可能な範囲で戻す。認証情報の代わりにアカウントの別名や設定ファイル内の項目名を記載する。
