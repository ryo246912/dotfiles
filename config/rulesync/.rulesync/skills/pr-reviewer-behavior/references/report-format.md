# スクリーンショット付きHTMLレポート

## 出力ファイル

- 保存先: 対象リポジトリの `.pr-reviewer-artifacts/<PR番号>/<実行識別子>/`
- ファイル名: 入力PRの `<PR番号>-<PRタイトル>.html`。例: `123-検索条件を追加.html`
- 実行識別子には日時とUUIDを使う。ディレクトリを排他的に新規作成し、衝突した場合はUUIDを再生成する。既存のレポートを上書きしない。
- タイトル中の `/`・`\`・`:`・`*`・`?`・`"`・`'`・バッククォート・`$`・`<`・`>`・`|`・制御文字は `-` にする。前後の空白・末尾の `.` を除き、ファイル名全体がUTF-8で255バイト以内になるようタイトル末尾を文字単位で短縮する。空なら `変更内容` を使う。
- PRタイトルをシェルへ直接展開しない。ファイルパスはファイルAPI等で安全に組み立てる。

## HTMLの要件

UTF-8で保存し、`<head>` の先頭付近（最初の1024バイト以内）に `<meta charset="utf-8">` を置く。単独で読めるHTMLを作る。`lang="ja"`、viewport、ページタイトルを設定し、CSSはHTML内に置く。
外部CDN・スクリプト・追跡用リソースには依存させない。PR本文・画面文言・入力値などはHTMLエスケープし、文字列をそのままHTMLとして挿入しない。
URLは `http` / `https` のみリンクに使い、認証情報や秘密のクエリパラメータを転記しない。

確認済みの各項目に、実際の操作後に撮影した結果画面を `<figure><img ...><figcaption>...</figcaption></figure>` として貼る。
PNG・JPEG・GIF・WebPの画像のみをbase64のdata URIで埋め込み、実データの形式とMIMEタイプ（`image/png`・`image/jpeg`・`image/gif`・`image/webp`）の一致を確認する。HTMLを移動しても見えるようにする。非対応形式は対応形式で再撮影し、できない場合は埋め込まず画像参照と理由を記載する。
キャプションには確認項目・操作直後の状態・何が確認できる画像かを記載する。
一覧表の証拠欄から該当画像へページ内リンクを張る。画像は横幅に収め、拡大して読める大きさで表示する。
秘密情報や個人情報がある画面は安全な範囲で撮影し直す。用意できない画像を捏造したり別項目の証拠に流用したりせず、撮影不可の理由を明記する。

## 本文の構成

### 対象と結果の概要

- 入力PRへのリンク・タイトル
- 検証に使った最上位PRへのリンク・stackの根拠
- 確認対象の変更範囲
- head SHA・環境との対応確認状況
- local／staging、検証URL、実行日時、使用したChromeの接続方法
- アカウント別名・ロール・テナント（秘密値は書かない）

### 手動準備・データ準備の手順

対象画面へたどり着くまでの準備と、確認データを作成・選択・更新するまでの手順を、実行順の番号付きで示す。
「一覧を開く」「行を選ぶ」「メニューを開く」「項目を選ぶ」などを一ステップずつ分ける。
各ステップは次の情報をひとまとまりにし、説明の直下に画像を埋め込む。結果セクションへの画像リンクだけでは代用しない。

1. ステップ番号・何をするか
2. 開くURL、クリックする画面文言、入力例・対象データ
3. 操作後にどうなればよいかと、実際に確認した状態
4. その操作対象または操作後の状態が分かるスクリーンショットとキャプション

操作対象が分かりにくいステップは操作前・操作後の画像を並べる。DB直接編集やコマンドで準備する場合は、秘密値を除いた実行内容・結果と、アプリ上でデータや状態を確認した画像を各ステップに添える。
既存データの再利用も、対象の見つけ方と選択手順を画像付きで示す。準備不要ならその旨を記載する。

### 準備済みデータ

用途、ID・表示名、状態・関連データ、開くURL、作成／再利用を表にする。

### 手動確認の手順

シナリオごとに、使用するアカウント別名とロール、最初に開くURL、画面上の文言を使った操作順、入力例・準備済みデータ、期待結果を番号付きで記載する。
手動確認も一操作ずつステップに分け、各説明の直下に操作対象や操作後の画面を必ず貼る。最終結果の画像だけで途中の手順を省略しない。準備手順と共通する場合は対応するステップを示し、同じ状態を表す画像をその箇所にも配置してよい。
認証入力画面は撮らずログイン後の状態を示す。未実行・撮影不可のステップは、画像の代わりにその理由を当該箇所に明記し、実行済みのように見せない。

### 実行結果とスクリーンショット

確認項目・仕様の根拠、操作、期待結果、実結果、未確認・続行条件、判定、証拠画像へのリンクを表にする。
実結果は観測した事実だけとし、契約・権限・SHA・flag等の未確認条件や次の確認操作は「未確認・続行条件」に分ける。
判定はPASSを緑、BLOCKEDとFAILを赤、NOT RUNを灰色のバッジで表示し、色だけでなく判定文字も必ず表示する。BLOCKEDは検証不能、FAILは実行して観測した不一致を意味する。同じ赤でも判定文字・説明で区別する。
判定は PASS / FAIL / BLOCKED / NOT RUN。実行していない項目をPASSにしない。
表の下に各項目のスクリーンショットとキャプションを配置する。

### 不一致・未確認事項

再現手順、期待と実際の違い、不具合／環境不足／仕様不明の区別、続行に必要な条件を記載する。
base比較は未実施のため、PR起因かは未判定とする。

### 後片付けと次回への引き継ぎ

残したデータ、削除方法、元に戻した既存データを記載する。
設定補完・知見の個別保存を行ったか、保存結果とその要点だけを書く。BLOCKED時も、保存を試行した場合はSAVED／NO_CHANGE／FAILED、設定先未確保、または知見保存先未初期化・読み取り専用等で未試行ならNOT_RUNと理由を記録する。設定内の認証情報は転記しない。

## 出力後の確認

手動準備・データ準備・手動確認の全ステップに対応画像、または未実行・撮影不可の理由があるか確認する。画像が当該ステップの状態と一致し、説明の直下に表示されることを確認する。
接続中のChromeで生成したHTMLを表示できる場合は、画像・リンク・表を確認する。
ツールや接続先の制約でローカルHTMLを開けない場合も、HTMLの構文・画像埋め込み・参照先を確認し、ブラウザでの表示は未確認と明記する。
最後に生成したHTMLのパスをリンクで渡す。リンク先は各パス要素をURLエンコードし、区切りの `/` は保持する。空白・`#`・`%` を含むタイトルでもリンクが壊れないことを確認する。
