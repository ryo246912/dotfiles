# UI/UX案の比較

1. 達成したいユーザーの目的、主な利用者、利用場面、成功条件と必須要件を、仕様・画面・既存プロダクトから確認する。既存案は比較に残す。推定で進められる項目は前提を明記し、選択が大きく変わる不足情報に限って質問する。
2. 下記の依存スキルを使い、実質的に挙動が異なる2〜3案を作る。各案で主要操作の順序、選択肢が見つかるか、操作ミスからの復旧、キーボードとモバイルの操作性を確認する。影響のある空・読込・失敗・権限・確認・取消の状態を扱う。
3. 全案について同じユーザータスク、サンプルデータ、画面幅、視覚的な作り込みで比較用の画像を作る。既存デザインシステムがあれば使う。ImageGenでワイヤーフレームを生成するか、画面内の文言や状態を正確に示す必要があればHTMLモックをブラウザでレンダリングして撮影する。案ごとの画像またはA/Bを明示した比較画像を本文に添付する。必要に応じ複数画面で操作の前後を示す。提供前に案と画像が一致し、文字が読めることを確認する。画像生成も撮影も利用できなければ、利用可能な可視化で補い、画像を添付できなかったことを記す。モックは試作であると明示する。
4. 各案の既存コンポーネント、データモデル、API、権限、状態、関連テストを調べる。仕様の複雑さと実装難易度をそれぞれ低・中・高で付け、難易度を左右する具体的な変更点を書く。低は主に既存部品で対応、中は複数箇所への変更、高は新しい状態管理・移行・大きな横断変更などを目安にする。QA、アクセシビリティ、既存利用者への影響、運用と戻しやすさも必要に応じて確認する。コードが参照できない場合は仮見積もりとし、未確認の依存を示す。
5. 必須条件で実行可能な案を判定し、UI/UX上の便益、仕様、実装の比較から推奨を出す。目的に応じた重要度を示す。一番の懸念、結論が変わる条件、必要なら判断のための最小限の検証を添える。

## 検討段階と責務

表の順に該当するスキルを呼び出す。共通の目的・必須条件・既存案と前段の結果を渡し、各段階は担当の成果を呼び出し元に返す。

| 順序 | 呼び出すスキル                    | 適用条件                                  | 担当する観点・返すもの                                                       |
| ---- | --------------------------------- | ----------------------------------------- | ---------------------------------------------------------------------------- |
| 1    | `brainstorming`（obra）           | 比較に値する案が不足している              | 操作方式が異なる候補を出す。候補が揃ったら次段に渡す。                       |
| 2    | `product-design`（mblode）        | 操作方式や挙動が比較対象に含まれる        | 各案の操作順、影響範囲、例外と復旧を定義し、比較できる粒度に揃える。         |
| 3    | `html-wireframe`                  | HTML モックを使って画面や状態を正確に示す | 確定した各案を同じ条件で描画する。ブラウザで撮影した比較画像を返す。         |
| 4    | `plan-eng-review`（gstack）       | 実装差が選択を左右する                    | 各案の実装への影響、既存部品の再利用、追加状態、移行・テスト負担を確認する。 |
| 5    | `tradeoff-analysis`（ysskrishna） | 具体案を比較して選ぶ                      | 前段の根拠を使い、必須条件、比較表、推奨、結論が逆転する条件をまとめる。     |

スキル一覧で名前と提供者を確認し、環境で利用できる完全名で呼び出す。専用の呼び出し機能がない環境では導入済みの `SKILL.md` を読んで担当手順を実行する。未導入・対象外の段階は理由を記録し、必要な検討は本スキルの手順で補う。親の PR レビューから渡された確認結果は再利用する。

案出しから比較までを繰り返さず、各段階では担当の観点を確認する。依存のインストール、製品コードの編集、コミット、外部投稿はユーザーが別途依頼した場合に行う。

## 返すもの

結論、案ごとの画像と主要フロー、UXの利点と欠点・仕様の複雑さ・実装難易度と根拠の比較表、結論が変わる条件と確認方法。参照した実装にはパスを添える。プロトタイプの生成先は一時作業領域とする。
