# 対応の十分性チェックリスト

実害の経路を、データ生成 → 判定・保存 → 読み出し → 出力 → 利用者の行動まで辿る。各観点で対象 SHA、検索語と範囲、根拠の `path:line`、実害との関係を控える。該当する箇所と通過条件を読み、確認できない経路は未確認として残す。

## 出口までの到達

- フラグ・列・API 項目が、利用者が見るすべての出口に届くか。一覧、詳細、別実装の複製コンポーネント、モバイル、CSV・Excel、メール・帳票、外部連携、管理画面を確認する。
- フラグ自体に加えて元データ・型・API・列定義・出力処理の識別子を grep して候補を全件洗い出す。フラグを一切参照しない出口も元データ側から見つけ、取得・整形・表示やファイル生成まで読む。
- 実害の経路にある出口へ届かず、問題が再発し得る場合は should 候補にする。

## ライフサイクル

- 状態が立つ条件と、確認後に下ろす・解除する・訂正する手段を確認する。UI、API、バッチ、再判定その他の書き込み経路を追い、既存の訂正で状態も更新されるかを確認する。
- 確認後に誰がどう直すか、その運用と権限が決まっているかを確認する。

## 既存データ

- 既存データに遡及・バックフィルが必要か。チケットの元の 1 件が直るか。
- 範囲外の場合は、関係者の合意と追跡先を確認する。

## 経路の網羅

- 同じデータを作る同期・非同期処理、再取得、再配信、フォールバック、別の解析経路で同じ判定が行われるか。共通処理を通る場合は呼び出し条件を確認する。

## 共有範囲

- データの行がテナント・チームをまたいで共有されるか。読み書きのスコープを辿り、別テナントに表示してよいかを仕様と照合する。

## 信号の質

- PR 本文の実測件数・割合を分母や計測条件と合わせて確認し、誤検知が多く利用者が印を無視するような設計になっていないかを確認する。
- 重さの違うケースが同じ扱いになっていないか。計測値がなければ件数や誤検知率を推定で断定しない。

## デプロイと互換

- マージ・デプロイ順序を確認し、旧版と新版が混在するときに読み書きが成立するか調べる。未知の項目の拒否（`extra="forbid"` など）とロールバック後の挙動も確認する。

## 範囲外の追跡

- PR 本文の「入れていないもの」ごとに後続チケットへのリンクがあるか。そのチケットが残った経路や作業をカバーするかを確認する。

## 観測

- 取りこぼし、判定件数、必要に応じて解除・訂正件数を後から確認できるログやメトリクスがあるか。出力条件と集計対象を辿る。
