## Bash ツールのシェルは zsh

Bash ツールのコマンドは zsh で実行される。bash の感覚で書くと、次の 4 つで失敗する。

- 引数に含まれるワイルドカードは必ず引用符で囲む（`--include='*.py'`、`-name '*.md'`、`'tests/**/*.py'`）
  - zsh は一致するファイルが無いと、コマンドを実行せずに `no matches found` で止まる
  - 一致しないかもしれないパスを展開するときは、glob に `(N)` を付けるか、`find` / `ls -d` で探す
- `=` で始まる語を引数にしない（`echo ====`、`echo =foo`）
  - zsh は先頭の `=cmd` をコマンドのパスに展開し、`==== not found` で止まる
  - 区切り線は `echo ----` か `echo '===='` にする
- 変数の直後に `:` を続けるときは、名前を `${B}` のように波括弧で囲む（`${B}:path`）
  - `$B:h`、`$B:t`、`$B:p` などは、zsh では修飾子として解釈される
- 空白区切りの文字列を変数のまま `for x in $F` に渡さない
  - zsh は引用符が無くても単語に分割しない
  - 配列（`F=(a b c)`）にするか、`${=F}` で分割する。リストを直接書いてもよい

迷うときは `bash -c '...'` で bash として実行してよい。ただし、PATH などの環境は zsh 側と同じとは限らない。

## コードレビュー・技術調査後のメモ記録

- PR レビューや技術調査が一区切りついたら、理解した内容を `plan/` ディレクトリ配下の `10-memo-xxx.md` のようなメモファイルに加筆する。該当するメモファイルがあれば追記し、無ければ新規に作成する。ただし、追記先のファイルが指定された場合はそのファイルに加筆する
- 「マークダウンに加筆して」「メモして」などと指示されたら、`plan/` ディレクトリ配下の `10-memo-xxx.md` のようなメモファイルに加筆する。該当するメモファイルがあれば追記し、無ければ新規に作成する。ただし、追記先のファイルが指定された場合はそのファイルに加筆する

## バックグラウンド worktree の成果物の返却

- バックグラウンドジョブが隔離用 worktree で作成したレビュー資料・調査メモなどの成果物（`plan/` 配下など）は、完了前に起動元 checkout の同じ相対パスへ自動でコピーする。ユーザーに手動コピーを依頼しない
- 隔離前に起動元 checkout の絶対パスと成果物の相対パスを記録し、隔離先と取り違えない。起動元が linked worktree の場合も、その checkout を返却先とし、別の main worktree を選ばない
- 成果物の作成・更新は隔離先で完了させる。返却時は絶対パスや `..` を含む相対パスを拒否し、実体が起動元 checkout 配下に収まること、コピー元・宛先と親ディレクトリが symlink でないことを検証する。別名で保存する場合も同じ検証を行う。検証後に必要な親ディレクトリを作成し、対象の通常ファイルだけを `cp --` する。コード変更や worktree 全体はコピーしない
- 隔離前にコピー先の存在状態と SHA-256 を記録する。返却時は起動元 checkout 内の成果物返却専用ロックを排他的に取得し、その保持中にパスを再検証し、存在状態・SHA-256 の比較、コピー、内容照合まで行う。ロックを取れない場合は上書きせず待機または未完了と報告する
- 開始時の状態が不明、または返却時に変更されている場合は既存ファイルを上書きしない。衝突しない別名を排他的に確保して保存し、その場所を報告する。ロックに従わない外部編集があり得る場合も既存ファイルは上書きせず別名で保存する
- コピーは削除・クリーンアップと別のコマンドで実行する。コピー後に内容が一致することを確認し、最終回答には起動元 checkout 側の成果物のパスを示す
- 実行環境の隔離制約や権限でコピーが拒否された場合は、別のツールで制約を回避せず、隔離先の成果物を保持してコピー未完了とその理由を報告する

## 同種ファイルへの修正適用

- 複数の同種ファイルに同じ修正を適用する場合、Glob ツールで対象ファイルを先に全件洗い出してから修正する
- 修正対象の一部だけに適用してユーザーへの確認なしに完了報告しない

## ツール呼び出しの失敗を減らす

- Claude Code では Bash の作業ディレクトリが呼び出しをまたいで保持されるため、毎回 `cd <dir> && ...` を前置せず、現在地を確認してから実行する。別ディレクトリのコマンドは絶対パスか `git -C <dir>` / `pnpm -C <dir>` などで指定する。Codex CLI など、呼び出しごとに作業ディレクトリを指定するツールでは `workdir` を明示する
- パスは推測しない。Glob / `git ls-files` で実在を確認してから Read / Edit する
- Edit が失敗したら、同じ `old_string` を再試行せず、Read し直して現在の内容から指定する
- 呼べるツールは、このセッションの一覧にあるものだけ。Claude Code で遅延ロードされるツールは ToolSearch で先に読み込む（他のツールでは対象外）
- コマンドが無い（command not found）場合は、同じ呼び出しを繰り返さず `mise ls` / `which` で確認し、無いことをユーザーに報告する
- 長くかかるコマンドは、`timeout` を明示するか、対象を絞って分割する
- `git commit` / `git push` / `gh pr create` は、`&&` やパイプで他のコマンドと連結せず、1 回の呼び出しにつき 1 つだけ実行する（CodeRabbit の PreToolUse hook が複合コマンドを拒否するため）
- hook や deny ルールにブロックされたら、同じ操作を繰り返さず、ブロックの理由を読む。ブロックを回避する手段は取らず、許可された範囲で別の方法を検討し、解決できなければユーザーに報告する

## コード変更の前に確認する

- リファクタリングや実装方針の「案」を求められた場合は、コードを変更せずに提案のみを行う
- 実装（ファイル編集）は「実装して」「コードに反映して」など、変更を明示的に依頼された場合のみ行う

## コードの書き方

- コードにはHow、テストコードにはWhat、コミットログにはWhy、コードコメントにはWhy notを書く
- ユーザーが明示的に指示しない限り、コードコメントやドキュメントには「なぜ別の実装にしなかったのか」以外を基本書かない
  - 特に、コードの内容をそのまま書き出しただけのHowのコメントやドキュメントは書かない
- 明示的な指示がなく、後方互換が必要ないリポジトリでは、後方互換の維持やデータ移行は行わず、常に理想的かつKISSなコードに書き換える

## ユーザーへのコードレビュー依頼

- 実装やプランが一区切りつき、ユーザーのレビューが必要なタイミングになったら、ユーザーの指示を待たずに自律的に crit を起動してレビューを依頼する

## Local development environment

- devcontainer内でPlannotatorのreview画面を起動したら、reviewerがfeedbackを送信するかsessionを閉じるまで、`plannotator annotate`のprocessを終了、background化、または再起動せずに待つ
- frontend、backend、databaseなど、host browserからaccessされるlocal serviceを起動するときは、次の順序を守る
  1. frontendとbackendのdevelopment server、およびSupabaseなど依存するlocal serviceを起動し、それぞれがcontainer内でlistenしていることを確認する
  2. host browserからaccessするすべてのportについて、`~/.config/devcontainer/scripts/ensure-plannotator-tunnel <port>`を実行し、SSH reverse tunnelを準備する
  3. 必要なportをすべて準備してから`plannotator annotate <URL> --app`をforegroundで起動する
- Plannotatorが自動で転送するのはannotation editorとlive-app proxyのportだけである。live appがbrowserから直接accessするAPI、Supabase、asset serverなどのportは自動転送されないため、漏れなく個別に`ensure-plannotator-tunnel`を実行する
- container内の`curl`だけで動作確認を完了しない。host browserと同じ経路でも画面操作、API request、認証などを確認する
- 例: Expo Webが`8081`、APIが`3000`、Supabase APIが`54321`でlistenする場合は、各serviceの起動後、Plannotatorの起動前に次を実行する

  ```bash
  ~/.config/devcontainer/scripts/ensure-plannotator-tunnel 8081
  ~/.config/devcontainer/scripts/ensure-plannotator-tunnel 3000
  ~/.config/devcontainer/scripts/ensure-plannotator-tunnel 54321
  plannotator annotate http://localhost:8081 --app
  ```

## コミットの粒度

- コード実装を依頼されている場合は、変更を未コミットのまま溜め込まず、意味のある作業単位が完了するたびにコミットする
- 1コミットには、単独で説明・レビューできる1つの目的に必要な変更だけを含める
- 無関係な機能追加、リファクタリング、フォーマット変更、依存関係更新、ドキュメント更新を同じコミットに混在させない。密接に関連し、分離すると不完全になる変更は同じコミットに含めてよい
- ステージ前に `git status --short`、`git diff`、`git diff --cached` で対象と既存の変更を確認し、意図したファイルだけをステージする。ステージ後に `git diff --cached`、`git diff --check`、`git diff --cached --check` でコミット内容を再確認する。既存の未コミット変更や他者の変更はコミットしない
- 各コミット時点で、可能な範囲のテスト・型チェック・lintを通し、ビルド可能で一貫した状態にする
- コミットメッセージは変更の目的が分かる簡潔な命令形にし、リポジトリに既存の規約がある場合はそれに従う
- 大きな実装は、準備的なリファクタリング、機能実装、テスト、ドキュメントなど、レビュー可能で依存関係が自然な順序のコミットに分割する。ただし、各コミットが壊れた中間状態にならないようにする
- コミットの実行を禁止された場合、またはユーザーによる確認が必要な場合はコミットせず、その理由と推奨するコミット分割を報告する

## 過去の指摘から学ぶ（agent-lessons）

- SessionStart で「agent-lessons: 過去のレビュー指摘から学んだ教訓」が注入されていたら、該当する作業ではそれに従って実装する

- Claude Code / Codex CLI でレビュー指摘を採用して直したとき、またはユーザーに実装を訂正されたときは、lessons-record skill で教訓を記録する

## PR作成後のレビュー対応

- git push と PR 作成までを依頼された場合は、PR を作成した時点で完了とせず、レビュー対応が終わるまで自律的に対応を続ける
  - この自律対応では、修正・コミット・push のたびにユーザーの承認を求めない
  - `pr-fix` の呼び出しでも、修正・コミット・push・CI と再レビュー待ちを自律的に行う
  1. PR のレビューコメント（人間・bot の両方）、CI、ベースブランチとのマージ可否を監視する。競合は pr-fix の手順に従って解消する。ユーザーが明示的に不要または延期と指定した場合は競合解消をスキップし、残っている競合を報告する
  2. レビュー指摘ごとに妥当性を確認し、妥当なものは修正してコミット・push し、lessons-record skill で記録する。修正しない指摘には、その理由をレビューのスレッドに返信する
  3. CI が失敗した場合は、ログから原因を調査して修正し、コミット・push する
  4. push 後は再びレビューと CI を監視し、新しい指摘があれば 2 に、CI の失敗があれば 3 に戻る
  5. 依頼済みのレビュー（人間・bot の両方）がすべて届き、未対応のレビュー指摘が無く、競合が解消済みか明示的にスキップされ、CI が通った状態になったら、対応内容をまとめてユーザーに報告して終了する。CI が通っただけで、まだ届いていないレビューがある段階では終了しない。ただし、一定時間待っても届かないレビューは未着として報告し、終了する
- 監視は `gh pr view` / `gh pr checks` / `gh api` などで状態を確認し、反映を待つ間は一定間隔で再確認する。短い間隔で無限にポーリングし続けない
- 次の場合は自己判断で進めず、状況と選択肢をまとめてユーザーに確認する
  - 設計方針の変更や大規模なリファクタリングなど、PR の範囲を大きく超える指摘
  - 指摘同士が矛盾している、または指摘の意図が読み取れない
  - 同じ指摘や CI の失敗が修正後も繰り返し発生し、原因を特定できない
- テストの skip・無効化や、force push による履歴の書き換えでレビューや CI を通そうとしない

## マージコミット作成後の確認

- マージコミット `M` を作ったら push 前に、やり直したマージ（`git merge-tree --write-tree M^1 M^2`。元のマージで `-X` を指定した場合は、`git merge-tree -h` で対応を確認して同じオプションを付ける。未対応なら対応する Git に更新してから検証する）の出力先頭の tree と `M` を `git diff --stat <tree> M` で比べる。コンフリクトしたファイル以外に差分が出たら、差分ごとに意図を確認し、フックの書き換えなどの意図しない変更だけを戻す。意味的な競合の解消などに必要な意図した変更は残す
- コンフリクトしたファイルは `git diff M^2 M -- <file>` で、相手側の変更がマーカーの外も含めて残っているかを確かめる
- コンフリクトしたファイルは `git diff M^1 M -- <file>` でも、第1親側の変更がマーカーの外も含めて意図せず失われていないかを確かめる
- リネームを含むファイルは各親の元のパスとマージ結果のパスを対応付け、`git diff -M M^1 M -- <第1親の元パス> <結果のパス>` と `git diff -M M^2 M -- <第2親の元パス> <結果のパス>` で確認する。リネームとして検出されない場合も、`git show M^1:<元パス>` / `git show M^2:<元パス>` と `git show M:<結果のパス>` の内容を比較する
